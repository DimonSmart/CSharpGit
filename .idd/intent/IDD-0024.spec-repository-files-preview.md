# Repository Files Tree and Preview

## Intent

The `Files` surface represents the complete file tree of the selected historical commit. It remains lazy at the commit-snapshot level: the snapshot is loaded when the Files tab is active, cached for reuse, and protected from stale asynchronous publication.

The Files tree and the main Repository tree share the same hierarchy-guide visual model. Their traversal/segment calculation and guide drawing are shared infrastructure rather than separate implementations. Name filtering computes hierarchy guides from the visible filtered tree.

## Selection and existing actions

A single logical file selection may originate from the Files tree or from Content Search results. Selecting a regular file shows a read-only preview automatically, including selection changes made by keyboard navigation or restored state. Content Search retains its matched line number as selection context for future navigation behavior.

Preview does not change existing action semantics. Double-click and Enter where already supported still perform `Open`; context actions still provide `Open`, `Open in editor`, and `Copy path`. Preview never edits a historical version.

## Preview behavior

Regular historical files support these baseline preview types:

- text, with bounded loading and language metadata for future syntax highlighting;
- PNG and JPEG images detected by actual content rather than file extension;
- binary/unknown fallback with file-size information.

A successful single-image preview exposes compact technical metadata next to the image: actual format, width × height, and file size. Image format and dimensions come from a shared bounded metadata-reading path that is also used by image diff. Image preview does not use a second, extension-based classifier.

A supported image signature alone is not sufficient to claim that an image is valid. Corrupt or incomplete headers are rejected safely. If metadata can be read but the UI decoder cannot render the pixels, the preview remains non-fatal and reports that visual preview is unavailable while retaining the metadata that was obtained reliably.

Folders show a neutral select-a-file state. Symlinks, submodules, and unsupported Git entries explain that preview is unavailable and are not materialized for preview.

Preview classification and bounded content loading are independent from UI rendering. Providers return semantic preview content, not UI elements, so additional viewers such as syntax-aware text, hex, audio, PDF, or archive viewers can be added without changing selection or Git historical-file loading.

## Image safety and bounded loading

Image metadata is read from bounded headers/segments without decoding the complete bitmap. Signature probing may use a small prefix, while formats such as JPEG may scan additional header segments up to a separate bounded metadata limit.

The compressed image preview limit remains independent from decoded-image safety. A file that exceeds the compressed preview limit is not handed to the bitmap decoder even when its metadata is readable.

Dimensions are validated before decoding. Excessive dimensions or decoded pixel count prevent bitmap rendering, and pixel-count calculations must be overflow-safe. These safety decisions apply consistently on Windows and macOS without platform-specific image parsing.

Large or malformed files must not cause unbounded reads, excessive bitmap allocation, modal failures, or application crashes.

## Historical file access

Presentation does not introduce a separate Git-reading path for preview. A regular file is resolved through the existing repository snapshot/file-version abstractions and materialized through the existing historical-file service. Cancellation is propagated through resolution, materialization, and preview loading.

Git commands, blob lookup semantics, and historical revision rules remain owned by the Application/Git layers. Preview classification operates only on the already materialized read-only local file.

## Concurrency

Preview remains responsive, cancellable, and stale-safe when selection, commit, repository, or active tab changes. A completed request may publish only if it still matches the active repository, commit and logical selection.

## Verification

Automated coverage verifies shared hierarchy traversal, filtered-tree guide segments, text encodings and language metadata, valid PNG/JPEG metadata extraction, content-based image detection, corrupt-image rejection, binary detection, bounded text loading, compressed/decode image limits, pixel-count overflow safety, stale preview publication, and architecture contracts ensuring the Files surface reuses the existing guide renderer, splitter, semantic historical-file services, and shared image metadata reader.

## Selectable Preview Text

- Text file preview remains a read-only selectable text surface with standard clipboard behavior and horizontal/vertical scrolling.
- Preview selection is purely presentation behavior and does not alter bounded loading, materialization, cancellation, stale-result protection or Git historical-file access.
