# IDD-0003.spec-repository-state

## Intent

Фактическое состояние Git-репозитория является единственным authoritative state
для истории, refs, working tree, index, stash, конфигурации и незавершенных Git
operations. UI может кэшировать данные, но не создает альтернативную модель,
способную разойтись с Git.

## Behavior

- Пользователь открывает существующий локальный репозиторий выбором папки;
  существующий Git worktree распознается и работает как обычный рабочий
  репозиторий.
- После действий, способных изменить репозиторий, приложение перечитывает
  фактическое состояние Git и обновляет затронутые области UI.
- Репозиторий может изменяться через CLI, IDE, другой Git GUI, filesystem или
  другой экземпляр приложения. Такие изменения автоматически отражаются в UI в
  разумный срок.
- Явная команда Refresh перечитывает фактическое состояние, включая
  незавершенные Git operations, без переоткрытия репозитория.
- При открытии репозитория, Refresh, возвращении приложения в активное состояние,
  завершении Git-команды и завершении внешнего merge tool состояние обновляется,
  когда это необходимо.
- Приложение учитывает global и repository-local Git configuration, когда она
  влияет на операции, и не дублирует стандартные Git-настройки без причины.
- Если выбранная интеграция требует установленный Git executable, его отсутствие
  или невозможность запуска диагностируются понятным сообщением.
- Пользователь может видеть и открывать связанные worktrees; создание, удаление,
  prune и расширенное управление ими не обязательны для первой версии.

## Durable Architecture And Constraints

- Кэши служат только производительности и никогда не становятся authoritative
  state.
- Низкоуровневый механизм Git integration — CLI, библиотека или комбинация —
  остается implementation decision при условии сохранения Git semantics,
  совместимости с реальными репозиториями и достаточной диагностики.
- Git-specific execution details скрыты за service layer.
- Application-specific configuration допустима для UI и поведения клиента;
  Git-owned настройки используют стандартную конфигурацию Git, когда это
  практически возможно.
- Реализация не фиксирует minimum Git version до появления функциональной
  необходимости.

## Non-Goals

- Собственная authoritative repository database.
- Предсказание результата mutating operation только из предыдущего UI-state.
- Полный worktree manager в первой версии.
- Фиксация конкретного механизма Git integration этим документом.

## Acceptance Criteria

- Обычный репозиторий и существующий worktree открываются корректно.
- Refresh отражает внешние изменения и незавершенные операции без переоткрытия.
- После любой поддерживаемой mutating operation UI соответствует реальному
  состоянию Git.
- Отсутствующий или неработающий Git runtime не оставляет UI в непонятном
  состоянии и не приводит только к необработанному exception.
- Изменения от другого экземпляра приложения впоследствии становятся видимы.

## Verification

- На реальных временных репозиториях проверяются открытие, refresh и обновление
  после внутренних и внешних изменений.
- Проверяется одновременное наблюдение одного репозитория несколькими процессами.
- Проверяется внешнее изменение refs, stash и деталей незавершенной Git operation
  без изменения HEAD/working tree; session обнаруживает semantic изменение и
  обновляет observable state/UI.
- Изменение только времени чтения, identity collection/wrapper objects или
  порядка refs/conflicts не считается изменением Git state.
- Проверяется корректное обнаружение linked worktree.
- Проверяются понятные failure-сценарии отсутствующего и не запускающегося Git
  runtime.
