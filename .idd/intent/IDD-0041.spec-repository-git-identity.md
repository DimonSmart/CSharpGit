# Repository Git Identity

## Intent

CSharpGit exposes the standard Git commit identity for the current repository as
`Settings → Identity`. The page lets the user view Git's effective
`user.name` and `user.email` and create or remove direct repository-local
overrides without creating a parallel CSharpGit settings system.

Related intent: IDD-0005, IDD-0011, IDD-0023, IDD-0039.

## Source of truth

- Git configuration is the only source of truth for repository identity.
- CSharpGit edits only direct repository-local `user.name` and `user.email`
  values through standard `git config --local` semantics.
- Identity is not persisted through `IAppSettingsService`, `settings.json`,
  or a CSharpGit repository-settings file.
- Effective configuration is resolved by Git with includes enabled and reports
  value, scope, and origin. CSharpGit does not reimplement `include` or
  `includeIf` resolution.
- The editable/removable repository override is a distinct concept from an
  effective value whose scope is local. Direct writable state is read from the
  repository scope with includes disabled.
- Name and Email inherit and override independently. There is no combined
  "Use global identity" state.

## Configuration precedence and worktrees

The page recognizes command, worktree, repository, global, system, and
not-configured sources. Included files keep the scope supplied by Git and expose
their actual origin.

A value included from repository configuration may therefore be effective with
source "This repository" while no direct repository override exists. CSharpGit
must not remove or edit that included file. Creating a direct local override may
shadow the included value; removing the direct override reveals the included
value again.

Worktree and command Git configuration can have higher precedence than a local
repository value. Those sources are read-only on this page. Saving a local
override remains allowed, but the UI warns that it may not become effective for
the current worktree or command environment. Worktree identity editing is a
separate future capability.

## Settings UX

`Identity` is a full Settings page between `General` and `Git Tools`.
It shows the current repository name/path and a "Commit identity" section with
independent Name and Email controls.

For each field the page shows:

- effective value;
- effective source;
- effective origin;
- whether a direct repository override exists;
- an editable buffer representing only the direct repository override.

When no direct override exists, an inherited effective value may be shown as a
placeholder but is not materialized into the editable buffer. Explicitly typing
the inherited value and saving intentionally creates a local override.

Clearing an existing local value means removal (`--unset-all`), not an empty
configured value. Empty input with no existing direct override is a no-op.
`Remove override` is independent for Name and Email and is disabled for an
included-only local value.

Without an open repository the page remains visible and shows a disabled
"Open a repository to configure its Git identity." state.

The open-repository application menu exposes `Repository settings…`, which
opens the existing Settings window directly on Identity. Reopening an already
open Settings window activates/revalidates the requested section even when
Identity is already selected.

## Validation and mutation

Name is trimmed, supports Unicode, and rejects CR/LF/NUL. CSharpGit does not
validate whether it resembles a person's legal or conventional name.

Email validation is intentionally soft: a non-empty value must have exactly one
`@`, non-empty text on both sides, and no whitespace/CR/LF/NUL. A dot in the
domain, RFC-complete syntax, or DNS validity is not required; values such as
`john@localhost` and `john+work@example.com` remain valid.

Save writes only dirty keys. Identity keys are treated as single-valued settings:
writes normalize duplicate direct values with replace-all semantics and removal
deletes all direct occurrences. After Save or Remove, CSharpGit rereads
authoritative Git state.

Name and Email are separate Git mutations rather than a transaction. On partial
failure CSharpGit stops further writes, rereads Git state, reports the failure,
does not attempt an unsafe rollback, and preserves unapplied user edits.

Opening, closing, navigating, refreshing, validating, changing repository, or
showing inherited placeholders never writes Git configuration.

## Repository switching safety

Editable identity state belongs to the normalized `WorkingDirectory` for which
it was loaded, not to a Repository object instance or only to
`GitCommonDirectory`.

When the active repository changes:

- clean Identity state automatically reloads the new repository;
- dirty Identity state is preserved but marked stale; Save and Remove are
  disabled until the user discards/reloads or returns to the original
  repository;
- every mutation rechecks the current repository immediately before writing;
- asynchronous reads use generation/current-repository checks so a late result
  from the old repository cannot publish into the new workspace.

This follows the repository-switching stale-result rules in IDD-0039.

## Commit semantics and boundaries

`user.name` and `user.email` are base Git identity configuration. The page
does not promise that they are the exact Author/Committer of the next commit:
Git may apply `author.*`, `committer.*`, command configuration, or
`GIT_AUTHOR_*` / `GIT_COMMITTER_*` environment overrides.

The normal CSharpGit commit workflow remains a standard `git commit` without
Identity-specific `--author` or author/committer environment injection.
Therefore, absent advanced overrides, Git naturally uses the configured local
`user.name` and `user.email`.

Authentication, credentials, GitHub/GitLab accounts, PAT/SSH configuration, and
commit signing are separate concerns and are not part of Identity.

## Architecture

Generic Git configuration mechanics are centralized in one Git-layer service
shared by Git Tools and Repository Identity. It owns Git config process
invocation, scope/origin parsing, include-aware effective/scoped reads,
direct no-includes reads, and generic set/unset behavior.

`IRepositoryIdentityService` exposes repository-independent application
semantics to Presentation. Presentation never invokes Git CLI directly and does
not depend on Uno types in the identity domain/application models.

## Acceptance criteria

- Settings navigation is `General → Identity → Git Tools → Diagnostics`.
- Effective Name/Email, source, and origin are shown independently.
- Direct local overrides can be created, normalized, and removed independently.
- Included local values are effective but not falsely removable.
- Worktree/command higher-priority values are visible and never rewritten.
- Global/worktree/system configuration is not mutated by Identity.
- No identity data is persisted in CSharpGit application settings.
- Repository changes cannot cause an old edit buffer or stale async result to be
  written/published for a different working directory.
- `Repository settings…` targets Identity while ordinary `Settings…` targets
  General.
- Existing Git Tools behavior continues through the shared config layer.
- Ordinary commits use Git's standard identity resolution without a parallel
  CSharpGit author/committer mechanism.
- Windows and macOS use the same Git semantics.
