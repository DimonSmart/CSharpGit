# IDD-0030 — Edit existing commit message

Status: Current

## Intent

CSharpGit provides a simple Edit commit message… action directly from History.
The user edits the full multiline message and CSharpGit performs the required Git
history rewrite without requiring a manual interactive rebase or CLI.

The action follows the selected-commit and refresh invariants of IDD-0014:
right-click targets the row under the pointer, Git semantics remain outside the
presentation layer, history-changing refresh keeps the existing Repository
identity, and selection follows the rewritten commit.

## Supported semantics

HEAD is edited with an amend operation that ignores the index. The repository must
be clean, HEAD must be attached to a local branch, the old tree and parent remain
unchanged, author metadata is preserved by Git, and external editors/signers are
not invoked.

An older commit is editable only when it is an ancestor of current HEAD and the
range from its parent through HEAD is linear. Root commits, historical merge
commits, detached HEAD, commits outside current HEAD ancestry, and ranges
containing merge commits are rejected by the simple editor.

Historical editing reuses the existing InteractiveRebasePlan and
StartInteractiveRebaseAsync workflow. The selected commit is Reword; later
commits remain Pick. CSharpGit does not implement a second history-rewrite engine.

## Safety and lifecycle

Staged, unstaged, and untracked changes block both HEAD and historical edits.
CSharpGit never stashes, resets, discards, pushes, force-pushes, or re-signs as an
implicit part of this action.

The Git layer owns validation, reachability/topology queries, amend-vs-rebase
choice, execution, cleanup, and old-to-new commit mapping. The UI only collects
the message, invokes the semantic operation, reports its result, and restores
selection.

Reword execution records the rewritten target SHA in CSharpGit-owned
.git/csharpgit-rebase/ metadata before replaying later commits. If replay stops
for conflicts, the existing RepositoryOperation.Rebase Continue/Abort lifecycle
remains authoritative. After Continue, selection follows the rewritten target;
after Abort it falls back to the original commit. Temporary support data is
removed after completion, abort, or a failure that did not leave an active rebase.

No operation automatically updates remote refs. A rewritten published branch is
shown through normal ahead/behind/diverged state and may later use the existing
force-push-with-lease workflow explicitly.

## Verification

Real-repository integration tests cover safe HEAD amend, multiline messages,
tree/parent/author preservation, dirty working-tree rejection, linear historical
rewrite, deterministic target mapping with duplicate messages and shared refs,
unsupported ancestry/root/merge/detached cases, active-operation rejection, and
temporary-data cleanup.

Presentation contract tests cover context-menu availability, right-click target
selection, use of CommitHistoryItem.Message, multiline input, blank/unchanged
guards, semantic-service delegation, history-changing refresh, and selection by
the SHA returned from the Git layer.
