# IDD-0018 — Manual refresh and semantic external repository change indicator

Status: Current

## Intent

CSharpGit keeps an opened repository as a stable UI snapshot until refresh is explicitly owned by the application.

Filesystem activity is not itself a repository change. `FileSystemWatcher` is a coarse invalidation mechanism only. Refresh Required means semantic probing has proved that Git-visible state affecting the displayed repository snapshot differs from the last successfully published displayed baseline.

A full repository refresh is performed only when:

- the repository is opened initially;
- the user explicitly invokes Refresh;
- a Git operation initiated by CSharpGit completes and its result must be reflected immediately.

Window focus, activation and deactivation never trigger refresh.

## External-change state machine

External change tracking has two lifecycle states:

```text
Armed
  ↓ semantic difference detected
Refresh Required / Suspended
  ↓ successful displayed baseline publication
Armed
```

Refresh Required is sticky/latched. Once a semantic probe proves that the displayed snapshot is stale, CSharpGit keeps the indicator red and suspends the external-change pipeline until a new displayed baseline is successfully published.

Returning the repository externally to an earlier state does not clear Refresh Required.

## RepositoryChangeMonitor

`RepositoryChangeMonitor` observes:

- the working directory;
- the worktree-specific `GitDirectory`;
- `GitCommonDirectory` for linked worktrees.

Metadata roots are deduplicated when one recursively contains another.

Filesystem notifications are trailing-edge debounced/coalesced. `RepositoryChanged` means only `repository may have changed`.

The monitor does not read Git state, history, refs or diffs and does not change UI state. It does not decide whether an event is Git-visible.

Obvious metadata lock noise such as `*.lock` and `index.lock` is ignored before probing. Other metadata activity remains coarse invalidation.

The monitor exposes an explicit lifecycle:

- `Start(repository)` starts a new armed monitoring session;
- `Suspend()` is idempotent and stops watcher work, cancels pending debounce and drops pending invalidation;
- `Resume()` is idempotent, recreates/re-enables watchers for the same repository and does not replay events that occurred while suspended;
- `Stop()` and `Dispose()` are safe from either state.

`Acknowledge()` is not part of the lifecycle.

Callbacks racing with `Suspend()` are harmless: monitor callbacks re-check suspended state, and orchestration refuses to queue semantic probes while Refresh Required is latched. A callback already handed outside the monitor before suspension may still arrive, but it must not cause a new semantic probe.

Invalidation generation remains monotonic. Suspension does not synthesize or replay generations.

## Semantic probe and displayed baseline

After a coalesced invalidation CSharpGit performs a local, read-only Git probe and compares the result with the displayed baseline.

The baseline represents the snapshot successfully published into the UI, not the latest state observed by the monitor.

The probe covers at least:

- HEAD/ref and detached state;
- staged/index state;
- unstaged tracked content;
- untracked non-ignored paths and content;
- local branches;
- remote-tracking branches;
- tags;
- stash entries;
- remote configuration that is displayed;
- repository-local merge-tool configuration that is displayed;
- merge/rebase/cherry-pick/revert/bisect state.

Repeated edits are significant even when XY status does not change. Therefore the probe includes semantic index object IDs and content fingerprints for Git-visible changed/untracked working-tree files.

Ignored files do not participate in the fingerprint. Git defines ignore semantics; CSharpGit does not implement a `.gitignore` parser.

Filesystem timestamps and raw `.git/index` bytes are not semantic equality.

## Displayed baseline revision

Every successful displayed baseline publication has a monotonically increasing `DisplayedRefreshBaselineRevision`.

The revision advances on every successful publication, even when the new fingerprint value is equal to the previous fingerprint value. Fingerprint equality therefore does not identify a baseline epoch.

A refresh that cannot produce a reliable fingerprint does not publish a baseline and does not advance the revision.

## Stale in-flight probes

Every semantic probe captures:

- repository identity;
- displayed fingerprint;
- displayed baseline revision.

After the asynchronous probe completes, its result may affect the UI only if:

- the repository identity is still current;
- the captured baseline revision still equals the currently published baseline revision.

Fingerprint equality alone is insufficient because a newer baseline epoch may contain the same fingerprint value.

A probe belonging to an older baseline revision is discarded completely.

## Local-only background behavior

Every Git command used specifically by the background probe runs with optional locks disabled:

`GIT_OPTIONAL_LOCKS=0`

The probe never performs network operations such as `fetch`, `ls-remote` or remote default-branch discovery.

Background probing never:

- opens/reopens the repository;
- loads commit history;
- loads a diff into the UI;
- modifies observable collections;
- changes selection;
- performs a full Refresh.

Probe failures keep the current indicator/lifecycle state, are diagnostic-only and do not themselves re-arm monitoring.

## Single-flight/coalescing

Background probes never run in parallel.

If filesystem invalidation arrives while a probe is running, CSharpGit marks one pending probe. When the current probe finishes, at most one additional probe runs for all invalidations accumulated in the meantime.

If the current probe detects a semantic mismatch:

```text
Refresh Required = true
monitor.Suspend()
pending probe = false
```

No additional semantic probe runs merely because an invalidation was already pending before the mismatch.

While Refresh Required is latched:

- new filesystem invalidations are not meaningfully processed;
- no new `IRepositoryRefreshProbe.ReadAsync` starts;
- no Git processes are initiated by the background refresh probe;
- the red indicator remains red.

There is no periodic Git polling.

`RepositoryStateSession` remains an explicit state holder with `Current`, `RefreshAsync`, `RunMutationAsync` and `StateChanged`, but it does not own a timer.

## Successful baseline publication and verification

Lifecycle recovery is tied to successful baseline publication, not to the Refresh button or to the name of a Git operation.

After a new displayed baseline revision is published, MainPage:

1. accepts the new fingerprint and revision;
2. clears the latched Refresh Required state;
3. resumes repository monitoring;
4. requests a post-baseline verification probe.

The watcher is active before verification starts.

The verification request closes races where repository state changes while the displayed snapshot is being refreshed or between snapshot capture and watcher re-arming. It participates in the same single-flight/coalescing mechanism as filesystem invalidations.

If verification detects a mismatch, Refresh becomes red again and monitoring is suspended again.

## Refresh failure

If Refresh fails before a reliable displayed baseline is published:

- the old baseline remains authoritative;
- baseline revision does not advance;
- Refresh Required remains latched;
- repository monitoring remains suspended.

The same rule applies when repository state loading succeeds but `IRepositoryRefreshProbe` cannot produce a reliable fingerprint.

## Refresh Required and UI

A watcher notification does not directly set `IsRefreshRequired`.

```text
filesystem activity
        ↓
coalesced invalidation
        ↓
local Git probe
        ↓
compare with displayed baseline + revision
        ↓
same      -> keep Refresh green
different -> Refresh red + suspend monitoring
```

External invalidation does not automatically rebuild any UI.

The Refresh toolbar button keeps three states:

- **Up to date** — static green Refresh icon.
- **Refresh required** — static red Refresh icon, tooltip `Repository has changed externally. Refresh to see the latest state.`
- **Refreshing** — yellow progress ring only for the explicit Refresh action, tooltip `Refreshing repository…`.

## Internal operations

Stage, Unstage, Commit, Checkout, Fetch, Pull, Push, Reset, Rebase, Cherry-pick, Revert, Stash, branch/tag operations and other CSharpGit mutations keep their existing post-operation refresh behavior.

Events caused by CSharpGit's own operation do not require file allowlists or per-operation watcher special cases.

If an internal operation successfully publishes a new displayed baseline:

```text
baseline revision++
latch cleared
monitor resumed
verification requested
```

This is true even when the new fingerprint value equals the previous one.

## RepositoryState equality

Semantic equality of `RepositoryState` is implemented once in reusable application logic.

`ReadAtUtc` is excluded.

Collections whose order is not semantically meaningful are compared order-independently.

## Linked worktrees

`Repository` exposes both `GitDirectory` and `GitCommonDirectory`.

For a normal repository they are equal. For a linked worktree they may differ. Shared refs, packed refs, remote-tracking refs, tags, stash and configuration under the common directory therefore remain observable.

## Verification

Automated coverage includes:

1. repeated edit of an already-modified tracked file changes the fingerprint;
2. repeated edit of an existing untracked non-ignored file changes the fingerprint;
3. ignored build/IDE/indexing activity leaves the fingerprint unchanged;
4. repeated external staging with unchanged XY status changes the fingerprint;
5. probe does not rewrite `.git/index`;
6. probe remains local-only even when an unreachable remote is configured;
7. working-tree changes publish an invalidation and multiple changes are debounced;
8. Git metadata changes are observed;
9. `Suspend()` stops working-tree and metadata notifications;
10. `Suspend()` cancels a pending debounced invalidation;
11. `Resume()` detects new changes again and does not replay suspended-period events;
12. repeated `Suspend()` / `Resume()`, `Stop()` while suspended and `Dispose()` while suspended are safe;
13. metadata lock files do not publish invalidation;
14. linked-worktree shared `GitCommonDirectory` changes are observed;
15. unchanged semantic probe keeps monitoring armed;
16. changed probe latches Refresh Required and suppresses further probe requests;
17. successful baseline publication clears the latch and re-arms monitoring;
18. publishing an identical fingerprint still advances baseline revision;
19. a probe from revision N is ignored after revision N+1 is published, even if both baselines have the same fingerprint value;
20. failed refresh / missing fingerprint does not publish a baseline;
21. post-baseline verification remains authoritative for changes racing with refresh;
22. `RepositoryStateSession` does not poll on a timer;
23. semantic repository-state collections compare independently of irrelevant ordering.

The user-visible acceptance criterion is that `dotnet build`, `dotnet test`, Visual Studio background activity and LocalVectorSearchMcp indexing can continuously modify ignored files while Refresh remains green, but once Git-visible state makes the displayed snapshot stale, Refresh turns red and the external-change pipeline becomes idle until a new displayed baseline is successfully published.
