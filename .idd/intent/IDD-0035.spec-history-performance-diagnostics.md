# History Performance Diagnostics

## Intent

CSharpGit provides an opt-in, bounded History performance capture that can distinguish ordinary scrolling cost from paging, Git activity, graph-layout churn, avatar work, allocation pressure, and work whose cost grows with loaded History size.

The diagnostic mode is measurement infrastructure, not a performance optimization. It must not reintroduce expensive production-path visual-tree traversal or change History rendering semantics.

## Behavior

- History performance diagnostics are disabled by default and are independent of normal file logging and log level.
- Enabling the setting exposes Start/Stop performance capture and Open diagnostics folder commands in History. Enabling the setting alone does not start a session.
- Only one capture may be active.
- A capture records privacy-safe repository-size metadata, ListView virtualization activity, render callback intervals, commit-graph lifecycle and geometry timings, topology conversion, layout publication, selected History scan categories, avatar presentation activity, process GC/allocation/CPU deltas, and Git command categories.
- A capture automatically stops after ten minutes and also stops on repository close/change, diagnostics disable, or application shutdown.
- Normal output is a JSON Lines file plus a human-readable summary. A normal stop writes `sessionSummary` as the last JSONL record.
- The JSONL writer is asynchronous and bounded. Diagnostic backpressure never blocks the UI hot path; dropped diagnostic records are counted.
- Slow-operation detail is bounded and aggregate duration statistics use fixed histograms rather than unbounded per-call samples.

## Hot-path constraints

When no capture is active, instrumentation performs only a cheap active-state check in already-instrumented call sites.

During capture, per-call instrumentation may use atomic counters and monotonic timestamps. It does not serialize JSON, write files synchronously, take stack traces, traverse the Visual Tree, execute Git, or scan History solely for telemetry.

The ListView `ContainerContentChanging` handler is attached only while a capture is active and performs O(1) accounting. Existing production scrolling optimizations remain intact.

## Privacy

Capture output does not contain repository paths/names, remote URLs, branch or tag names, commit messages or SHAs, author names/emails, file contents, diffs, Git stdout/stderr, Git working directories, or full Git arguments.

Git commands are represented only by aggregate user/internal and command-category counts.

## Verification

Automated coverage verifies settings defaults/persistence/live application, bounded diagnostic structures, privacy contract, temporary virtualization subscriptions, graph reason instrumentation, scrolling/layout guardrails, and all required termination paths.

Desktop lifecycle coverage continues to verify that graph recycling remains correct and that no recursive graph-layout or avatar-configuration traversal is reintroduced.

## Non-Goals

- changing Uno version;
- changing History paging or page size;
- changing ListView virtualization;
- changing the commit-graph algorithm;
- changing avatar caching policy;
- changing Git loading architecture;
- optimizing a bottleneck before capture data identifies it.
