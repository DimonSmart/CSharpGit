# IDD-0020.spec-release-distribution

## Intent

CSharpGit распространяется как готовое desktop-приложение через GitHub Releases.
Windows и macOS являются обязательными release-платформами; Linux остаётся
best effort. Версия релиза определяется Git tag формата `vMAJOR.MINOR.PATCH`.

- IDD-0002

## Behavior

- Разработчик инициирует новый patch release из clean `main` командой
  `publish-next-version.bat`.
- Команда обновляет `main` только fast-forward, определяет предыдущий корректный
  release tag в истории `main`, создаёт следующий annotated tag и атомарно
  отправляет `main` и tag в `origin`.
- Первый release tag при отсутствии предыдущих release tags — `v0.1.0`.
- Push корректного release tag запускает GitHub Actions release pipeline.
- Release создаётся только после успешных build/test и успешной упаковки:
  - Windows x64;
  - macOS Apple Silicon;
  - macOS Intel.
- Linux x64 собирается и публикуется при успехе, но его ошибка не блокирует
  Windows/macOS release.
- Windows artifact является self-contained; пользовательский executable —
  `CSharpGit.exe`.
- macOS artifacts содержат `CSharpGit.app`; приложение пока не подписывается и
  не notarize-ится.
- Linux executable называется `CSharpGit`.
- Release artifacts не содержат `.pdb`.
- Version metadata готовых artifacts соответствует версии release tag.
- Для каждого опубликованного artifact release содержит проверенный SHA-256 в
  `SHA256SUMS.txt`.
- Release notes формируются из Git history и явно описывают runtime-зависимость
  от `git`, статус macOS signing/notarization и best-effort статус Linux.
- Повторный запуск release pipeline для того же tag обновляет существующий
  GitHub Release и artifacts, а не создаёт второй release.
- После успешного Release отдельный workflow обновляет `Casks/csharpgit.rb` в
  `main` на основе `SHA256SUMS.txt`.
- Homebrew Cask поддерживает Apple Silicon и Intel artifacts и устанавливает
  `CSharpGit.app`.
- До первого реального release Cask в репозитории является bootstrap metadata;
  реальные version/SHA-256 записываются Homebrew workflow после релиза.
- Готовая программа на всех платформах требует установленный `git` в `PATH`.
  .NET SDK является только development dependency.

## Durable Architecture And Constraints

- Git tag является единственным источником release version; release не требует
  ручного изменения version в `.csproj`.
- Обычный CI и release pipeline разделены: CI проверяет `main` и pull requests,
  но не публикует release artifacts.
- Release workflow должен оставаться расширяемым для будущих способов
  распространения без включения их в текущую задачу.
- Release pipeline не должен запускать интерактивный GUI ради smoke checks.
- Signing, notarization, WinGet, MSI/MSIX, APT/DEB/RPM, Snap, Flatpak и
  встроенный auto-update не являются частью текущего поведения.

## Acceptance Criteria

- CI выполняет restore/build/test на Windows, Linux и macOS для `main` и PR.
- Локальный publish script выбирает `v0.1.0` без предыдущих release tags и
  увеличивает только PATCH для последующих релизов.
- Release tag автоматически создаёт Windows x64 и оба macOS artifacts,
  `SHA256SUMS.txt` и GitHub Release.
- Linux artifact добавляется только при успешной best-effort сборке.
- Обязательные artifacts имеют ожидаемые executable/app names, корректные
  version metadata и не содержат `.pdb`.
- Homebrew metadata может быть восстановлена вручную для существующего tag без
  создания нового release.
- README разделяет installation готового release и development requirements.

## Verification

- Проверять YAML syntax и release job dependencies без создания реального tag.
- Проверять алгоритм выбора версии изолированно; реализация задачи сама не
  создаёт `v0.1.0`.
- Реальный end-to-end release проверяется отдельным явным запуском
  `publish-next-version.bat`.
