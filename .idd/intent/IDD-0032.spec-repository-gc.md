# Repository Garbage Collection

## Intent

CSharpGit provides an explicit repository optimization command for users who want to run ordinary Git garbage collection and see what changed in Git object storage.

The first version is deliberately limited to repository GC. It does not introduce a general maintenance framework, scheduled/background maintenance, or unrelated cleanup commands.

## Behavior

- The main menu exposes Optimize repository between More Git operations and Settings.
- The command is available only with an open repository, while the UI is idle, while no Git repository operation is active, and while another repository maintenance run is not already in progress.
- Before execution CSharpGit reads Git object-storage statistics with count-objects -v and shows only loose objects, packed objects, pack files, and combined object-storage size.
- The UI never presents count plus in-pack as a synthetic unique object count.
- The dialog offers three typed options, all off by default: aggressive optimization, prune unreachable objects now, and keep largest pack.
- Prune-now explicitly warns that recently lost objects can become unrecoverable and that another external Git process must not write to the repository concurrently.
- With no options selected, execution is exactly ordinary git gc.
- The three options map deterministically to --aggressive, --prune=now, and --keep-largest-pack in that order.
- The running dialog remains open, prevents repeat execution and ordinary closing, and uses indeterminate progress rather than parsing Git output.
- The application window cannot close while GC is running.

## Architecture and Concurrency

Repository maintenance is exposed through a dedicated application abstraction. Git-specific parsing and CLI argument construction remain in the Git layer, and every Git process runs through the shared GitCommandExecutor.

GC uses the same repository mutation gate as other CSharpGit mutations. No second semaphore or maintenance runtime is introduced. Busy state remains active for the serialized operation.

The result distinguishes failure of git gc from failure of later statistics or presentation refresh. A successful GC remains successful even when after-statistics or a targeted UI refresh fails.

## Refresh

After successful GC, CSharpGit reads object-storage statistics again and shows Before and After values plus the change in object-storage size.

The serialized workflow performs local-only repository-state refresh. Commit history is reread only when reflog display is active. Worktree presentation is refreshed because GC can remove stale worktree administration metadata.

The operation does not perform unconditional RefreshAll, remote refresh, fetch, or other network work.

## Worktrees

The command is supported from both a primary repository and a linked worktree. Git commands run from Repository.WorkingDirectory and rely on Git to resolve the shared object database.

## Non-Goals

- fsck, prune, maintenance, repack, reflog-expire, remote-prune, or worktree-prune commands;
- automatic or scheduled GC;
- progress percentages or stdout-based progress;
- GC cancellation in the first version;
- calculating the full repository, working-tree, or .git directory size;
- custom pack analysis or direct object-database traversal;
- arbitrary presentation-provided Git command-line arguments.

## Verification

Automated coverage verifies count-objects parsing, overflow and malformed input handling, typed option mapping and order, command visibility in the Git Console, execution from ordinary repositories and linked worktrees, shared mutation coordination, menu placement, close blocking, targeted local refresh, reflog-specific history refresh, worktree refresh, and the absence of unconditional full/network refresh.
