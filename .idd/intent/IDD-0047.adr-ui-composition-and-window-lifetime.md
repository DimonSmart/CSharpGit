# IDD-0047.adr-ui-composition-and-window-lifetime

## Status

Accepted

## Context

A shared MainPage with feature-specific partial classes, subscriptions, dialog
handlers and cross-feature state obscured ownership and made shutdown and testing
fragile. The completed workspace refactoring separates visual composition,
feature behavior, repository state and the native window lifetime. Preserve the
repository session, mutation and stale-result guarantees in IDD-0039, the feature
boundaries in IDD-0042 and IDD-0043, and the testable Core boundary in IDD-0044.

## Decision

### Composition and dependency direction

- MainPage.xaml is the declarative visual root, with Uno-generated code-behind
  only. Do not add authored MainPage partials, root event-handler attributes,
  feature implementations or forwarding facades. Compose the repository launcher,
  explorer, history, working tree, file preview and Git console as separate
  feature surfaces.
- App is the application composition root and owns IHost, native application
  events and shared services. WindowSessionFactory creates one DI scope per
  window, resolves the window-local dependencies and obtains the visual root
  from WindowWorkspaceComposition. WindowSession does not reference MainPage.
- WindowWorkspaceComposition explicitly wires Views, controllers and lifecycle
  callbacks using typed dependency groups and narrow contracts. It is not a
  feature workflow owner. Do not introduce a global or window service locator,
  universal UI action interface, event bus, global service bag, or synthetic
  UI events to dispatch semantic commands. DI resolution stays in the
  composition roots.
- Views own visual composition, bindings, local UI mechanics, projections and
  their subscriptions. Feature ViewModels own authoritative feature state,
  semantic commands and application-service orchestration. Do not create a
  ViewModel per View merely for symmetry. Feature ViewModels must not depend on
  XAML, MainPage, IServiceProvider or sibling ViewModels.
- Focused controllers/coordinators own UI workflows and cross-feature
  interactions via explicit inputs, operation-specific contracts and callbacks;
  they must not access other Views' private state. Dialogs use the owning
  window's XamlRoot and existing shared ContentDialog serialization gate.
  Behaviors are small local UI event adapters; services perform focused work,
  not arbitrary access to UI or other services.
- HistoryWorkspaceView owns the declarative Summary, Changes and Files tabs;
  do not construct these tabs dynamically from the root composition.
  WorkingTreeView and HistoryWorkspaceView own their selection, diff and
  viewport interactions. RepositoryFilesSurface owns historical browsing,
  search and selection; focused controllers own preview and file actions.
  Repository projection, idle continuations, toolbar, keyboard and status
  interactions have explicit local owners rather than a shared shell facade.
- OpenRepositoryViewModel remains the repository lifecycle and feature
  composition owner, with the existing repository context, session cancellation
  and shared admission/mutation gate. UI extraction must not create another
  repository state, selection authority or mutation/refresh path. Capture
  requests before awaits and reject results/actions for stale repository or
  selection identities.

### Window ownership and shutdown

- App owns application-wide services, including the shared settings state,
  avatar/repository image caches and Git command activity history. Repository,
  feature and window UI state must not be registered as singletons. Each
  window receives its own scope, repository ViewModel, feature instances,
  controllers and composition. A DI-created disposable model has one owner:
  the window scope, not an additional cascading disposal path.
- WindowSession owns initialization, the one-way Created -> Active ->
  PreparingForShutdown -> Disposed lifecycle (including direct cleanup after
  failed initialization), and release of its scope. It does not execute Git
  commands. Native window callbacks and host shutdown remain at the application
  boundary.
- WindowCloseSafetyProvider reads the current operation owners' state.
  WindowCloseCoordinator decides admission; WindowCloseOrchestrator sequences
  native close and managed shutdown. Reject close during protected operations;
  recheck protection and window identity after asynchronous draft confirmation.
  Native close and application restart share one window-local commit-draft
  confirmation owner. Keep the existing platform-specific close ordering:
  macOS schedules managed cleanup after the native close callback returns and
  stops the host before final native close; Windows/Linux preserve their
  authorized native close paths.
- WindowWorkspaceLifetime in Presentation.Core owns workspace preparation
  and completion sequencing. Composition registers explicit callbacks.
  Preparation closes admission before invoking callbacks and shares one
  in-flight result across repeated/reentrant requests. Cancel pending UI
  work, previews, dialogs and monitoring; observe preparation failures
  without skipping remaining callbacks or diagnostics. Completion invokes
  all registered cleanup callbacks at most once and aggregates failures.
  Failed initialization or completion before preparation must not permit
  subsequent work against disposed controls.
- Each feature detaches the subscriptions it owns before the scope is disposed.
  Unloaded is not final disposal. Late async callbacks must not publish to
  closed controls or a different workspace; preserve repository, generation
  and selection fences and marshal bindable notifications through the UI
  dispatcher. Release native bindings and UI resources before disposing the
  window scope; keep the host alive until window cleanup allows shutdown.
- Diagnostics shutdown has a bounded three-second wait in the outer close
  orchestrator. Timeout or a cleanup exception must not prevent mandatory
  cleanup and final close. Do not apply this diagnostic timeout to protected
  Git mutations or use it as permission to interrupt them.

### Verification

- Keep executable architecture guardrails for the declarative root, explicit
  composition, absence of service location, feature ownership and subscription
  symmetry. Keep behavioral Core tests for lifetime preparation, reentrancy,
  error aggregation, repeated shutdown and completion on initialization failure.
- For changes affecting composition or lifecycle, acceptance requires the
  actual production desktop smoke and build/test matrix on Windows, macOS and
  Linux. CI must require the desktop check rather than silently skip it when
  no graphical session is available (CSHARPGIT_REQUIRE_DESKTOP_CHECK=1; Linux
  uses Xvfb with Openbox). Local headless runs may skip GUI tests but do not
  count as desktop acceptance.
- The smoke exercises real MainPage bindings, repository/worktree opening and
  switching, Files tab activation, Working Tree/History navigation, graph
  rendering/resize, and native close/lifecycle protocol. Verify the actual
  tested commit and test results, not an older green run or a source-only
  check. Use typed diagnostic contexts rather than private page fields or
  an experimental XAML-only probe.
- Manual native-dialog/accessibility and long-running protected
  rewrite/maintenance/update acceptance are separate from the automated smoke;
  do not infer their results, visual performance, or race safety solely from
  structural checks.

## Alternatives Considered

- Retain feature code in MainPage partials or a universal facade: rejected
  because shared private state, implicit dependencies and lifecycle ownership
  would remain.
- Put every workflow into the root ViewModel or composition: rejected because
  it would recreate the same monolithic owner under a different name.
- Use a service locator or event bus for cross-feature access: rejected
  because dependencies, admission and cleanup would become implicit.
- Rely on Unloaded, duplicate disposal or force process exit for shutdown:
  rejected because transient visual detachment is not window disposal and
  protected operations and cleanup must retain explicit ownership.
- Accept only headless tests or an isolated XAML probe: rejected because
  production bindings and native lifecycle behavior would remain unverified.

## Consequences

Feature behavior and cleanup can evolve independently while retaining shared
repository safety and the single-workspace product contract. Composition may
wire more explicit dependencies but must not accumulate feature logic.
WindowWorkspaceLifetime remains Uno-free so sequencing is testable without
a graphical desktop; real desktop acceptance still requires the supported
platform matrix. No user-visible behavior change or multi-window product
support is implied by the per-window ownership model.

## Supersedes

None. Refines IDD-0002, IDD-0042 and IDD-0043; their current decisions remain
authoritative for their respective scopes.
