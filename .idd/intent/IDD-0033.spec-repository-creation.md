# Repository Creation

## Intent

CSharpGit can initialize new local Git repositories without conflating repository creation with repository opening.

Repository initialization remains a Git-owned operation. CSharpGit supplies validated paths and typed creation intent, while Git creates and owns repository metadata.

## Behavior

- A Personal repository is a normal working-tree repository initialized with ordinary `git init <path>`.
- A Personal repository may be initialized in a new directory, an existing empty directory, or an existing project directory containing user files. Existing user files are preserved.
- Creating a nested Personal repository inside another repository is allowed when the selected target is not itself already a repository.
- A Central repository is a bare shared repository initialized with `git init --bare --shared=all <path>`.
- A Central repository may be created only in a new directory or an existing empty directory.
- A target that is already the root of a normal repository, linked worktree, or bare repository is rejected rather than silently reinitialized.
- Personal repository creation opens the resulting repository as the current workspace after initialization succeeds.
- Central repositories have no working tree, are not opened as ordinary CSharpGit workspaces, and are not recorded in Recent repositories.
- Switching to a newly created Personal repository protects any unapplied commit-message draft before filesystem or Git changes begin.
- If initialization succeeds but opening the new Personal repository fails, the repository remains on disk and the previous usable workspace is preserved when possible. Creation is not rolled back destructively.

## Repository State

A newly initialized Personal repository with no commits is a valid application state.

An unborn symbolic HEAD is not detached HEAD. Its symbolic branch name remains available to presentation even before a corresponding local branch ref exists.

History for both All references and Current branch is empty before the first commit. The application handles the confirmed unborn-HEAD case specifically rather than treating arbitrary `git log` failures as empty history.

Working-tree operations remain available before the first commit, including untracked-file discovery, staging and the first commit. After the first commit, ordinary branch refs and history appear through the existing refresh flow.

## Architecture

Repository creation is a dedicated application capability separate from `IRepositoryService`, whose responsibility remains opening repositories.

All Git CLI execution, including initialization and repository-boundary probes, goes through `GitCommandExecutor`. Actual initialization is user-visible Git command activity; validation probes are internal activity.

Git creates repository metadata. CSharpGit does not synthesize `.git`, bare repository structure, initial commits, README files, licenses, gitignore files, or initial branch refs.

Repository creation failures use typed creation-specific failure reasons. They remain distinct from repository-opening failures. Cancellation remains cancellation and is not converted into a repository creation failure.

## Non-Goals

- Clone;
- remote hosting repository creation;
- automatic README, LICENSE, or .gitignore generation;
- automatic initial commit;
- initial branch selection;
- using a bare repository as a normal workspace;
- adding bare repositories to Recent repositories.

## Verification

Automated coverage verifies path validation, existing-repository boundary detection, nested repositories, preservation of existing project files, bare/shared creation, creation activity classification, cancellation and Git failure semantics, unborn repository state and history, first-commit transition, dependency injection and architecture guardrails, required UI entry points, draft protection, and path-based workspace switching.
