# IDD-0018 — Manual refresh and external repository change indicator

Status: Current

## Intent

CSharpGit keeps the opened repository as a stable displayed snapshot until a full refresh is explicitly owned by the application.

`FileSystemWatcher` is only an invalidation source. It does not prove that Git-visible state changed and it does not rebuild repository state.

Refresh Required means:

> after the displayed baseline was published, Git-visible working-tree state or relevant Git metadata changed, so the displayed snapshot may be stale.

This is deliberately conservative. Refresh Required is sticky until a newer full refresh is successfully published.

A full repository refresh is performed only when:

- the repository is opened initially;
- the user explicitly invokes Refresh;
- a Git operation initiated by CSharpGit completes and its result must be reflected immediately.

Window activation/focus does not trigger repository refresh.

## External-change model

External invalidation is split into two classes:

1. working-tree filesystem activity;
2. relevant Git metadata activity.

Working-tree activity is checked semantically with one read-only:

```text
git status --porcelain=v2 -z --untracked-files=all
```

using `GIT_OPTIONAL_LOCKS=0` (or an equivalent no-optional-locks mechanism).

Relevant Git metadata activity can immediately latch Refresh Required without running Git.

The background pipeline never performs a repository-wide state read merely to decide whether Refresh should turn red.

## WorkingTreeStatusSnapshot

The displayed working-tree baseline is a compact semantic snapshot built from parsed porcelain v2 records.

It includes the Git-visible information already present in porcelain v2 records, including:

- staged and unstaged state;
- untracked paths;
- conflicts;
- rename/copy records and original paths;
- submodule state;
- index modes/object IDs carried by porcelain v2.

Its collections compare independent of output order.

It does not include:

- filesystem timestamps;
- raw `.git/index` bytes;
- content hashes calculated by CSharpGit;
- tags, remotes, stash, config, or a repository-wide set of refs.

Full Refresh and background checking use the same porcelain-v2 parser.

## Baseline publication

A full repository refresh already executes `git status --porcelain=v2`. The displayed `WorkingTreeStatusSnapshot` must be produced from that existing status result.

Publishing a baseline must not launch an additional Git process.

Every successful displayed baseline publication advances a monotonically increasing baseline revision, even when the working-tree snapshot value is equal to the previous value.

A failed refresh does not publish a baseline and does not advance the revision.

## Repeated edits and path-aware invalidation

Status equality alone is not enough.

If a file was already modified or untracked when the baseline was published, another edit can leave porcelain status text semantically unchanged while the displayed diff/content becomes stale.

Therefore working-tree invalidation is evaluated as:

```text
watcher paths
    +
current git status
```

Refresh Required is latched when either:

- the current status snapshot differs from the displayed snapshot; or
- the snapshots are equal, but an invalidated path intersects a path Git currently reports as changed/untracked/conflicted/etc.

Directory invalidation intersects Git-visible descendants.

For dirty submodules, an event below the submodule root intersects the submodule status entry.

Renames consider both current and original paths.

No `git hash-object` content fingerprinting is used.

## Ignored files

CSharpGit does not parse `.gitignore`, nested ignore files, `.git/info/exclude`, or global excludes.

Git is the source of truth.

If an ignored path changes, the watcher may cause one status check. If the status snapshot is unchanged and the invalidated path does not intersect a Git-visible status path, Refresh remains green.

## RepositoryChangeMonitor

`RepositoryChangeMonitor` observes:

- the working directory;
- the current worktree-specific `GitDirectory`;
- shared `GitCommonDirectory` metadata for linked worktrees.

It only converts filesystem activity into coalesced `RepositoryInvalidationBatch` values.

A batch retains:

- monotonic generation;
- whether working-tree activity occurred;
- whether relevant metadata activity occurred;
- whether event detail was lost/overflowed;
- bounded working-tree paths;
- bounded metadata paths.

Renames retain both old and new paths.

Generation advances immediately when an accepted filesystem event arrives, before debounce publication.

The monitor never:

- reads Git;
- parses ignore rules;
- reads index state;
- hashes file contents;
- changes UI state;
- decides whether the displayed snapshot is stale.

## Relevant Git metadata

Relevant private metadata for the current worktree includes at least:

- `HEAD`;
- `index`;
- `config.worktree`;
- merge/rebase/cherry-pick/revert/bisect operation metadata used by the application.

Relevant common/shared metadata includes at least:

- `refs/**`;
- `packed-refs`;
- `config`;
- `logs/refs/stash`;
- `info/exclude`;
- sparse-checkout metadata when applicable.

Known high-volume/transient noise does not itself latch Refresh Required:

- `*.lock`, including `index.lock`;
- `objects/**`;
- `COMMIT_EDITMSG`.

Unknown metadata may conservatively be treated as relevant.

### Linked worktrees

For a linked worktree, private metadata of sibling worktrees under:

```text
GitCommonDirectory/worktrees/<other>/**
```

must not invalidate the currently opened worktree.

The current worktree still reacts to its own `GitDirectory` and to shared common refs/config/stash metadata.

## Sticky Refresh Required

After a confirmed invalidation:

```text
RefreshRequired = true
```

the state remains latched until a successful newer baseline publication.

While latched:

- the Refresh icon remains red;
- no new background `git status` is launched;
- no repository-wide probe is launched;
- pending status-check work is dropped;
- watcher activity may continue only for generation/race tracking.

The watcher is not suspended merely because Refresh Required is red.

## Single-flight background status

At most one background working-tree `git status` may run at a time.

If more working-tree events arrive while it is running, they are coalesced into one pending invalidation batch. After the current check finishes:

- if Refresh Required became latched, pending work is discarded;
- otherwise at most one next status is started for accumulated invalidations.

A relevant metadata event during an in-flight status can immediately latch Refresh Required. The completed status result must not clear the latch.

There is no periodic polling.

## Stale async results

Every background status check is associated with:

- repository identity;
- displayed baseline revision;
- invalidation generation.

A completed result may affect UI state only if the repository and baseline revision are still current and Refresh Required was not already latched.

Results belonging to an older baseline are ignored.

## Background status failure

After a working-tree invalidation, failure of the background status check means CSharpGit cannot prove that the displayed snapshot is current.

Unless the request became stale or was cancelled by shutdown/repository switch, the safe result is:

```text
RefreshRequired = true
```

with diagnostics.

## Refresh races

At the beginning of a full refresh, capture the monitor generation.

The watcher remains active during the full refresh.

After successful baseline publication:

- if generation did not advance, clear Refresh Required and do not run any post-refresh Git command;
- if relevant metadata changed during refresh, conservatively re-latch Refresh Required without Git;
- if working-tree activity occurred during refresh, run at most one additional status check and apply the same path-aware comparison against the new baseline;
- watcher overflow/error during refresh re-latches safely.

Raw invalidation history/generation is authoritative even if debounce publication occurs after the new baseline. A late debounced callback for an invalidation already accounted for by the refresh race check must not trigger a duplicate status.

If the full refresh fails, the old baseline/revision remains authoritative and accumulated invalidations are not discarded.

## Internal Git operations

Stage, Unstage, Commit, Checkout, Fetch, Pull, Push, Reset, Rebase, Cherry-pick, Revert, Stash, branch/tag operations and other CSharpGit mutations retain their normal post-operation refresh behavior.

Do not maintain per-operation watcher event allowlists.

A successful application-owned refresh publishes the new working-tree baseline and uses the same generation race rules as manual Refresh.

## Removed background architecture

External-change monitoring must not use a repository-wide semantic fingerprint.

Background tracking must not call these merely to determine Refresh Required:

```text
git config --list
git remote -v
git stash list
git for-each-ref
git for-each-ref refs/tags
git ls-files --stage
git hash-object
```

It must not load history, tags, remotes, stash, repository config, full RepositoryState, diffs, or working-tree file contents.

The old concepts `IRepositoryRefreshProbe`, `GitRepositoryRefreshProbe`, `RepositoryRefreshFingerprintBuilder`, and `RepositoryRefreshFingerprint` are not part of external-change monitoring.

## Diagnostics

Background working-tree checks are identifiable as a dedicated logical operation such as:

```text
WorkingTreeChangeProbe
```

and normally contain exactly one Git command.

Refresh Required diagnostics distinguish reasons such as:

- StatusChanged;
- GitVisiblePathInvalidated;
- MetadataChanged;
- WatcherOverflow;
- StatusProbeFailed.

Diagnostics must make it possible to see why Refresh became red and to detect accidental reintroduction of a multi-command background probe.

## Performance requirements

For one ordinary tracked-file edit:

```text
filesystem events
→ debounce
→ <= 1 git status
→ RefreshRequired
```

For a repeated edit of an already modified or untracked path, the same one-status budget applies and no content hashing is allowed.

For ignored-only activity, at most one status may run and Refresh remains green when Git-visible state/path intersection is unchanged.

For relevant metadata activity:

```text
filesystem event
→ RefreshRequired
background Git commands = 0
```

After Refresh Required is latched:

```text
background Git commands = 0
```

until a new baseline is successfully published.

A full refresh with no concurrent invalidation performs zero additional verification Git commands after baseline publication.

A working-tree event during refresh permits at most one additional status.

## Git-native optimizations

CSharpGit must work correctly without requiring `core.fsmonitor` or `core.untrackedCache`.

If Git-native optimizations are enabled by the repository/user, ordinary `git status` may naturally benefit from them.

CSharpGit does not directly implement the FSMonitor protocol or invoke `git fsmonitor--daemon` as part of this feature.

## Verification

Automated coverage protects at least:

- clean tracked-file external edit;
- repeated edit of an already modified tracked file;
- new and repeatedly edited untracked files;
- ignored-only activity;
- staged/index changes and repeated restaging;
- delete/rename/conflict/submodule status interpretation;
- current-worktree private metadata;
- shared linked-worktree refs;
- sibling-worktree private metadata isolation;
- lock/object-database noise filtering;
- debounce/path accumulation;
- single-flight status behavior;
- stale result protection;
- refresh-time generation tracking;
- watcher overflow safety;
- status failure safety;
- command budget: one status for working-tree checks, zero Git for metadata, zero Git after latch.

The user-visible contract is: ignored background filesystem activity does not make Refresh red when Git-visible state is unchanged, but once the displayed snapshot may be stale, Refresh becomes red and background Git work becomes idle until the application successfully publishes a new baseline.
