# IDD-0044.adr-settings-contracts-and-testable-core-boundaries

## Status

Accepted

## Context

Settings persistence is implemented by `JsonAppSettingsService` in a single JSON document.
The original `IAppSettingsService` exposed UI appearance, Git workflow, diagnostic and
repository launcher operations to consumers that usually needed only a few members.
Tests also compiled 96 linked copies of 91 production source files directly into
`Application.Tests` and `Desktop.Tests` (five were linked in both test assemblies).
This made assembly visibility, package dependencies and real production ownership
difficult to verify.

Architecture Stabilization stages 1 and 2 already fixed repository-session ownership,
captured file action requests and the shared mutation gate. Assembly separation must
not change those guarantees or any user-facing behavior.

## Decision

Introduce four functional interfaces in Application Abstractions:

- `IAppearanceSettings` for theme, commit time, history rendering/reflog, and avatars.
- `IGitWorkflowSettings` for push/pull defaults and autostash.
- `IDiagnosticsSettings` for the **atomic** logging pair, Git Console, and history telemetry.
- `IRepositoryLauncherSettings` for repository directory, recent items, groups and pinning.

Each extends `IAppSettingsChangeSource`. The compatibility interface
`IAppSettingsService` inherits all four, without defining a new persistence layer.
`JsonAppSettingsService` remains the only implementation and persisted-state owner.
DI aliases resolve the same object. A successful update publishes committed state
before invoking `Changed`, outside the write semaphore. Callbacks can read newer
state, run on any thread, and need not be raised for a recognized no-op; subscribers
must re-read current values. Existing cancellation, file format, fallback, path
handling, exceptions and atomic file writes remain unchanged.

Introduce `CSharpGit.Infrastructure.Core` and `CSharpGit.Presentation.Core`,
both `Microsoft.NET.Sdk` / `net10.0`, for neutral services, state, algorithms
and feature ViewModels. The Uno `Infrastructure` retains native folder picker
and other platform adapters; the Uno `CSharpGit` executable retains XAML,
controls and UI dispatcher. `IUiDispatcher` belongs to Presentation.Core, but
`UiDispatcher` stays with the UI host.

Assembly owners are defined by their **single production compilation**.
The initial extraction compiles the original source files as linked sources in
the appropriate Core projects, and excludes those exact files from the original
Uno projects. This preserves existing source-contract test paths while ensuring
every type is compiled into one production assembly only; tests now reference
that real compiled assembly. Physical source-directory moves may follow once
contract-test path resolvers are migrated, without changing assembly ownership.
Production source files must never be compiled into test assemblies.

The neutral project-reference graph is acyclic: Domain is a leaf; Application
depends on Domain; Git depends on Application/Domain; Infrastructure.Core
depends on Application/Domain; Presentation.Core depends on Application/Domain.
Neither Core references Uno, platform assemblies or desktop adapters.
Platform hosts may depend on their respective Core projects and the application
layer. Grant narrowly scoped internal access via `InternalsVisibleTo` rather
than making internal types public solely for tests.

## Alternatives Considered

Separate persistence services or event buses per settings facet: rejected due
to drift, lost concurrent updates, and different publication semantics.

Move every XAML-dependent ViewModel into Core: rejected due to excessive
changes to bindings and platform-specific contracts. In particular
`RecentRepositoriesViewModel` and `RepositoryTreeNode` remain in Uno.

Keep compiling production sources into unit-test projects: rejected because
the unit tests would continue using assembly-distinct copies of application
types rather than the shipped production assembly.

Immediately relocate all physical source files while rewriting every
source-contract test: deferred to avoid introducing unrelated regressions
in existing UI and architectural guardrails. The compile-time ownership
boundary is enforced immediately.

## Consequences

`RepositorySyncViewModel` accepts `IGitWorkflowSettings`;
`HistoryViewModel`, `OpenRepositoryViewModel` and `ApplicationThemeManager`
consume `IAppearanceSettings`; the recent-repository UI obtains launcher
and appearance facets. `SettingsViewModel` remains a justified aggregate consumer.
Existing settings JSON remains compatible. Source-boundary guardrails and
platform packaging must be verified independently of unit-test compilation.
There is no change to product intent or repository session semantics.

## Supersedes

None.
