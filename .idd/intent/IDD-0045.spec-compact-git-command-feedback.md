## 1. Цель и продуктовые принципы

Добавить в CSharpGit **опциональный расширенный режим визуального сопровождения пользовательских Git-команд** (Advanced Git Command Feedback).

Когда режим включён, пользователь должен быстро получить ответы на три вопроса:

1. **Какую команду Git действительно запустило приложение?**

2. **Что сейчас происходит?** В том числе видеть потоковый вывод и Git progress.

3. **Завершилась ли конкретная Git CLI invocation успешно?**

Компактное представление также имеет образовательную ценность: пользователь узнаёт соответствующие Git CLI-команды. Основной элемент — фактическая безопасно отображённая команда, а не большой лог.

**Не создавать второй Git Console, просмотрщик логов или терминал.** Для подробностей использовать существующую Git Console. В выключенном состоянии новая функция не меняет UX, Git execution, сообщения об ошибках и политику автоматического открытия Git Console.

Область действия — **Git CLI invocation с `GitCommandKind.User`**, а не произвольная длительная UI-операция или внутренние запросы Git. Визуальная надпись `Completed successfully` утверждает только, что **данный Git-процесс** завершился успешно (`exit code 0`), но не что весь составной workflow приложения успешно завершён.

## 2. Подтверждённое исходное состояние

В существующем коде уже есть:

- `GitCommandExecutor`: запускает Git без shell, параллельно считывает stdout/stderr, публикует activity после успешного `Process.Start`.

- `GitCommandActivityHistory`, `IGitCommandActivitySink`, `IGitCommandActivitySource` и `GitCommandActivityChangedEventArgs`: единый механизм истории и событий.

- `GitCommandKind.User` / `Internal`; `GitCommandStatus.Running` / `Succeeded` / `Failed` / `Cancelled`; `GitCommandActivityChangeKind.Started` / `Output` / `Completed` / `Cancelled`.

- В событии `Started`/финальном событии есть `Activity`; у события `Output` **нет полного `Activity`**, вместо него передаются `ActivityId`, `OutputStream`, `OutputChunk` и `OutputRequiresResync`.

- `GitCommandActivity.DisplayCommand` уже формируется из реальных effective arguments с существующим маскированием (включая автоматически добавляемый применимой политикой `--progress`).

- `GitConsoleView`, `MainPage.GitConsole.cs`, `GitCommandConsoleState`, `GitOutputDisplayBuffer`, `GitOutputTextEscaper`; существующий output batching для Git Console — около 75 мс.

- В `GitCommandActivityHistory` лимит **100 записей**; при вытеснении сейчас удаляется также запись из `_byId`. Следовательно, `Get(id)`, дальнейший output и terminal event для вытесненной ещё работающей activity **сейчас теряются**. Это реальный дефект граничного сценария, который нужно учесть в работе.

- Output history ограничен **1 MiB на stdout и 1 MiB на stderr для каждой activity**; поток предварительно редактируется/маскируется, обрезка обозначается `[output truncated]`.

- `GitConsoleAutoOpenMode` (`OnErrors` / `Always` / `Never`) по IDD-0022; Git Console внутри `RepositoryWorkspace` непосредственно над status bar. Сам `RepositoryWorkspace` отсутствует при показе стартового экрана.

- Clone имеет **собственный `ContentDialog`**, progress/busy-state и кнопку отмены (`MainPage.RepositoryCloning.cs`). Его не заменять вторым диалогом.

- Настройки разделены по фасетам в соответствии с IDD-0044; `JsonAppSettingsService` — единственный persistence owner, `Presentation.Core` не зависит от Uno.

**Нормативные ограничения:** IDD-0022 (Git Console), IDD-0034 (presentation sanitization), IDD-0040 (Clone), IDD-0042 (sync ownership), IDD-0044 (settings и testable Core). Не вводить новый Git runner или новый независимый collector.

## 3. Настройки

В `Settings → Diagnostics` добавить компактную секцию **Git Command Feedback**, рядом с существующими настройками Git Console, с двумя ToggleSwitch, числовым полем длительности (0–30 секунд) и пояснениями на английском языке. Настройки глобальные и общие для всех репозиториев.

### 3.1. Show Git command progress dialog

- Тип: `bool`.

- Начальное значение и fallback при отсутствующем/старом JSON-поле: **`false`**.

- Текст: `Show Git command progress dialog`.

- Описание: `Show a compact panel with the actual Git command, live output, and execution result.`

- Предлагаемое свойство контракта: `IDiagnosticsSettings.ShowGitCommandProgressDialog`.

- Предлагаемый метод: `SetShowGitCommandProgressDialogAsync(bool value, CancellationToken)`.

При `false`: не создавать/не показывать активное compact view, не выполнять его stream processing и таймеры; оставить неизменными existing auto-open, status bar, Git Console и error UX.

При `true`: показывать User activity, если её presentation context допускает компактное представление. `Internal` команды не показывать автоматически. Выполнение самих Git CLI-команд от настройки **не зависит**.

### 3.2. Automatically close after successful completion

- Тип: `bool`; default/fallback **`false`**.

- Текст: `Automatically close after successful completion`.

- Описание: `0 closes immediately; 1–30 seconds keeps a successful result visible. The countdown pauses while you interact with the dialog.`

- Предлагаемое свойство: `IDiagnosticsSettings.AutoCloseSuccessfulGitCommandFeedback`.

- Предлагаемый метод: `SetAutoCloseSuccessfulGitCommandFeedbackAsync(bool value, CancellationToken)`.

- UI разрешает изменить настройку только если `Show Git command progress dialog == true`; сохранённое значение при выключении основного переключателя **не сбрасывать**.

При `false` успешный результат остаётся до ручного закрытия, переключения на другую команду или завершения срока жизни host. При `true` успешно выполненная **видимая floating activity** автоматически скрывается по истечении настраиваемого времени от 0 до 30 секунд (по умолчанию 5 секунд) **видимости terminal success state**. Для embedded presentation действует lifecycle родительского operation dialog: компонент не должен искусственно задерживать его закрытие после успешного workflow (§6.2). Для Failed и Cancelled автозакрытия нет. Никакого таймера от момента `Started`.

Пока указатель находится над компактной карточкой, либо любой её интерактивный элемент имеет keyboard focus, отсчёт **приостановлен с сохранением остатка**, а не перезапущен. Когда взаимодействие прекращается — отсчёт возобновляется. При переключении activity, ручном скрытии, выключении режима или уничтожении host таймер отменяется. Настройка длительности `SuccessfulGitCommandFeedbackDurationSeconds` сохраняется вместе с остальными; значение 0 означает немедленное скрытие после успешного завершения.

### 3.3. Persistence и реакция на изменение

Хранить все три значения в существующем `JsonAppSettingsService`/`SettingsState`, без второго файла и без отдельного settings service. Использовать единый `Changed` и правила атомарного сохранения IDD-0044. `SettingsViewModel` показывает сохраняемые значения и откатывает UI после save failure. Применять изменения без перезапуска:

- Выключение основного режима немедленно скрывает текущий compact view, завершает его наблюдение/таймеры, **не отменяет Git**; существующая Git Console продолжает работать.

- Включение действует для **новых** User invocations. Не открывать ретроспективно историю старых команд.

- Изменение автозакрытия действует для текущего видимого успешного результата: при включении отсчёт стартует заново с сохранённого интервала (по умолчанию 5 секунд); при выключении таймер отменяется.

- В обработчиках `Changed` заново считывать committed state; событие может прийти с фонового потока. Не привязываться к порядку отдельных write notifications.

### 3.4. Совместимость с `GitConsoleAutoOpenMode`

**Не удалять и не переинтерпретировать** существующие значения `GitConsoleAutoOpenMode` в JSON и старом UI.

| Compact mode | Событие | Автоматическое открытие Git Console |

| --- | --- | --- |

| Off | Любое | Строго прежние правила `Always / OnErrors / Never` |

| On, компактное представление реально обслуживает User activity | Её Started/Failed | Не открывать Console **автоматически для этой же activity** |

| On, feedback недоступен / не может быть создан / операция требует fallback | Её Started/Failed | Применить прежнюю политику Console; не скрывать ошибку |

| On | Internal activity | Сохраняется прежнее поведение (Internal сами не открывают панель) |

Условие suppression вычислять по **activity ID и реальному маршруту отображения** (root compact / embedded), а не по одному глобальному `bool`. Не подавлять ранее вручную открытое состояние Console и не закрывать Console от имени нового режима. `OnErrors` не должен автоматически раскрывать Console **в дополнение** к уже обслуживающему ту же команду компактному view; application-level error message при этом остаётся.

Если пользователь нажимает `Open Git Console`, это явное действие: открыть существующую панель и выбрать **именно эту activity**, не менять общий auto-open mode. Чтобы избежать визуального наложения, обычную compact-карточку можно скрыть для этой activity. Ошибочные автодействия и открытие details для другой команды недопустимы.

## 4. UI / UX

### 4.1. Размещение и кроссплатформенность

Предпочтительный вариант для операций из workspace — **модальный центрированный слой внутри `RootLayout`** с затемнением, удержанием клавиатурного фокуса внутри него и блокированием интерфейса приложения на время отображения, а не отдельное OS window. Именно `RootLayout`, а не только `RepositoryWorkspace`, обеспечивает правильное владение и доступность UI в состоянии без открытого репозитория. Для Clone использовать **тот же reusable content component, встроенный в существующий `ContentDialog`** вместо второй floating card.

- Не перехватывать focus при появлении; текст в рабочей области не должен терять введённый текст.

- Использовать полноэкранный затемняющий hit-test overlay, перекрывающий основной интерфейс и предотвращающий случайные клики мимо диалога.

- Карточка не блокирует navigation, editing, selection, opening other dialogs или Git commands.

- Положение и размеры адаптируются к окну и scaling Windows/macOS. Ориентиры: ширина \~420 logical px, желательная минимум \~360 px при наличии места, максимальная высота \~280 px, output viewport \~100–140 px, отступы 12–16 px. Если места мало — ограничивать размеры до доступной области, не выталкивать кнопки или статус за экран.

- При открытой нижней Git Console карточка не должна перекрывать её необходимые controls; соблюдать приоритет явного ручного открытия. При активных модальных dialogs вне Clone — не создавать поверх них конкурирующий modal/topmost UI, использовать предусмотренный fallback либо безопасно скрыть floating presentation.

- Light/Dark, density и spacing соответствуют IDD-0019; стандартные Fluent/Uno controls, без Windows-only оконного API.

### 4.2. Структура компактной карточки

1. **Header:** `Git command` + status `Running…` / `Completed successfully` / `Failed` / `Cancelled`, небольшой spinner только при Running; после завершения — duration, при Failed — exit code, если известен. Для unknown exit code не показывать фиктивный `exit 0` или `exit -1`. `Completed successfully` получает общий `SuccessStatusTextStyle` с `SystemFillColorSuccessBrush`; для других статусов возвращается нейтральный `BodyTextStyle`. Никаких hard-coded green RGB или цветовых индикаторов без текста.

2. **Command (главный элемент):** фактический `GitCommandActivity.DisplayCommand`, моноширинный, контрастно отделённый от output, с переносом/ellipsis по высоте. Пример: `git pull --progress origin main`. Полная **безопасная** текстовая версия — в tooltip и по `Copy command`. Если аргументы намеренно скрыты существующей security policy, не пытаться восстановить их. Copy и tooltip получают одну безопасную строку. Shell-like формат — **информационный**, он не гарантирует одинаковую исполнимость во всех shells.

3. **Live output:** единый небольшой selectable/read-only моноширинный viewport; объединённое human-readable preview потоков stdout/stderr, в котором допускаются неопределённости межпоточного порядка. Без поиска, отдельного списка команд, export и терминальной эмуляции.

4. **Actions:** `Copy command`, `Open Git Console`, `Hide` (Running) / `Close` (terminal). Не добавлять Stop/Cancel процесса: скрытие **никогда** не отменяет CLI или целый workflow.

Экранные тексты интерфейса — **английские**; имена кнопок использовать последовательно в UI и AutomationProperties. Навигация с клавиатуры и доступные accessible names обязательны. При появлении не выполнять auto-focus; при ручном tab-focus доступ к действиям должен сохраняться. Status не должен кодироваться одним только цветом.

### 4.3. Live-output semantics

- Показать вывод по мере поступления events; stdout и stderr читаются и обслуживаются независимо на уровне execution/history, но в карточке выводится **один** компактный список актуальных строк.

- Git progress обычно пишет в stderr с `\r`: повторные updates **перезаписывают логическую строку**, а не наращивают тысячи progress-строк.

- Повторно использовать `GitOutputDisplayBuffer`/`GitOutputTextEscaper` на Presentation boundary; при необходимости выделить общий reusable bounded preview adapter в `Presentation.Core`.

- Не передавать в XAML literal NUL/unsafe control characters, ANSI escape sequences и непроверенные machine-readable delimiters. Сохранять IDD-0034: `\0` для NUL, `\xNN` / `\uXXXX` для прочих UI-unsafe controls, допустимые CR/LF/tab с существующей progress-семантикой.

- Инкрементальный output уже приходит из **sanitized** `IGitCommandActivitySource`; не подключаться к raw process pipes и не обрабатывать секреты новым небезопасным путём.

- Preview ограничивается **последними 32 KiB UTF-8 байт безопасного отображаемого текста** (ориентир фиксированной product policy для v1); при достижении лимита удалять старые logical lines / фрагменты без утраты актуальной `\r` строки и показывать ненавязчивое `Showing recent output. Open Git Console for details.` Отдельно сохранять существующий `[output truncated]` от capture layer: это **другой** вид обрезки.

- При ручной прокрутке вверх не срывать scroll-to-end; когда пользователь вернулся вниз, follow-tail возобновляется. Не терять viewport-position без причины при небольших обновлениях.

- Пустой вывод: показывать нейтральное `No output yet`/`No output`; output не обязателен для сообщения об успехе.

- Не обещать global byte ordering stdout + stderr: порядок наблюдения отдельных streams может отличаться от реального порядка записи процесса.

## 5. Lifecycle отображения

### 5.1. Started и первоначальная задержка

Для `Started(User)` сохранить `ActivityId` и безопасный command snapshot, определить presentation owner; создать логическое состояние ожидания и запланировать **один** показ спустя **150 мс**. Это защита от мерцания, а не попытка скрыть короткие команды.

- Если команда ещё `Running` по истечении 150 мс, показать состояние Running.

- Если она завершилась до 150 мс, показать **сразу final state** без flash Running.

- Даже быстрый успешный CLI показывает финальное состояние на заданное число секунд после фактического появления/отрисовки (по умолчанию 5). Значение 0 является исключением: успешный результат скрывается сразу.

- `Started` регистрируется после `Process.Start`; при pre-start failure event не будет (см. §5.7).

- Output может прийти до обработки поставленного в UI queue `Started`; coordinator должен либо принять события по известному ID, либо один раз взять `Get(id)` и синхронизироваться с накопленным состоянием при показе. Нельзя терять первые чанки.

### 5.2. Потоковое обновление, throttle и resync

`Output` events имеют `ActivityId`, stream, chunk, `OutputRequiresResync`, **но не Activity snapshot**. Маршрутизировать их только на соответствующую текущую activity. На UI передавать пачки, ориентировочно раз в **75–100 мс** (как Git Console), без dispatcher job на каждый символ. При интенсивной выдаче ограничивать накопленный pending payload/buffer, не наращивать необработанную очередь.

Если событие требует `OutputRequiresResync`, запросить `IGitCommandActivitySource.Get(activityId)` для соответствующего потока и восстановить presentation-safe state из snapshot. Если source больше не содержит activity, применять согласованную политику активной activity из §7.4; не показывать данные другой команды и не придумывать недостающий вывод.

Финальное событие должно доставить остаток output и окончательное состояние. Если terminal notification пропущена или Started пришёл позже Completed, видимая Running-карточка сверяет состояние того же ActivityId с IGitCommandActivitySource при первом Capture и затем с ограниченной частотой, а не на каждом UI tick. Если activity вытеснена из истории и достоверного состояния нет, нельзя бесконечно показывать Running либо придумывать успех.  UI state **монотонен**: после `Succeeded`/`Failed`/`Cancelled` старое queued `Started`, `Running`, `Output` или delayed timer не может вернуть Running или перезаписать newer activity. Допустимы поздние безопасные output fragments той же activity только если они ещё относятся к captured state и не нарушают однократную terminal status transition. Для корректности использовать generation/ID guards и, при необходимости, snapshot reconciliation.

### 5.3. Succeeded

Показать `Completed successfully`, duration и сохранённый безопасный command/output preview; spinner остановить. Auto-close по §3.2. **Не объявлять успешным UI-workflow**, если после CLI требуется refresh, parse, checkout/open или другая проверка.

### 5.4. Failed

Показать `Failed` и известный exit code; автоматически **не закрывать**. Показать последние полезные stderr/stdout строки в пределах compact viewport и оставить `Open Git Console`. Existing user error notifications/typed exceptions не отменяются. Не показывать второй конкурирующий **полноразмерный** dialog ошибки только ради нового feedback; компактная карточка — вспомогательная диагностика, а не замена error handling.

### 5.5. Cancelled

Показать `Cancelled`, остановить spinner, сохранить достигнутый preview, не закрывать автоматически. Скрытие окна не трактовать как cancellation. У Clone и других workflow существующие safe Cancel mechanisms остаются владельцами отмены. Если процессы принудительно завершаются при закрытии приложения, продолжать соблюдать текущие lifecycle guarantees.

### 5.6. Исключительная ошибка после запуска процесса

В текущем `GitCommandExecutor` catch path может записать `Cancelled` не только при `OperationCanceledException`, но и при **некоторых иных аварийных исключениях после Process.Start** (I/O/pump/callback/cleanup). Это нельзя представлять пользователю как его добровольную отмену. При реализации исправить **узко соответствующий activity lifecycle**: реальная cancellation → `Cancelled`, non-cancellation execution failure → `Failed` (exit code может быть `null`), без изменения exception flow, process cleanup и application-level Git result semantics. Допустимо минимальное совместимое расширение sink/events или эквивалентная корректировка после изучения всех callers; существующие тесты executor обновить. Не записывать фиктивный exit code.

### 5.7. Ошибка до `Process.Start`

Если Git отсутствует, путь недоступен, запрещён запуск и `Process.Start` не произошёл, `Started` сегодня не публикуется. **Не создавать фиктивную activity** и не оставлять бесконечный Running. Существующее user-facing сообщение об ошибке обязательно; compact view для такой invocation может отсутствовать. Создание новой cross-layer error activity не требуется первой версией. Для Clone сохранить typed GitUnavailable error из IDD-0040.

### 5.8. Hide, Close и ручной переход

- `Hide`/`Close` фиксирует **dismissal именно текущего activity ID**. Её следующие Output/Completed не должны снова сами показывать ту же карточку.

- Git продолжает работу; его output и итог сохраняются по существующей history policy.

- **Следующая новая** User invocation снова может показать compact view; скрытие не равно глобальному отключению режима.

- `Open Git Console` передаёт **именно целевой ID**. Если activity уже вытеснена из history, не выбирать автоматически «похожую» или последнюю другую запись под видом нужной; дать нейтральное `This command is no longer available in Git Console history.` и обеспечить обычное ручное открытие Console без ложной selection, если это уместно.

## 6. Конкуренция команд и специализированные dialogs

### 6.1. Одно автоматически показываемое компактное представление

В пределах главного окна может быть не более **одного видимого автоматически показываемого экземпляра**: либо root modal card, либо embedded feedback в текущем operation dialog. Одна activity идентифицируется по `Guid`, а не по названию subcommand или текущему repo. Не создавать стек toast windows.

**Детерминированная политика выбора (v1):**

1. Видимый **непрочитанный Failed** terminal state имеет приоритет перед новым Running/Succeeded. Новая успешно завершённая команда не скрывает ошибку незаметно. Если возникает новый Failed, он заменяет предыдущий в compact view; предыдущая ошибка остаётся в Git Console и existing error UX.

2. Когда такой Failed не удерживается, показывать **последнюю начавшуюся User invocation** (новая Started заменяет предыдущую карточку, отменив её show/close timers). Историю не копить внутри карточки.

3. Если несколько User invocations уже Running, а показываемая завершилась, **не переключаться самопроизвольно** на старую фоновую activity — её ход и результат доступны в Console. Следующее явное User действие переключает карточку на новую activity. Это предотвращает неожиданные всплывания старого progress.

4. `Cancelled` требует ручного закрытия только пока это текущая видимая invocation; `Started` нового пользовательского действия может заменить её. `Succeeded` заменяется новой User invocation либо auto-close. Если старая activity завершилась уже невидимой, её event не должен менять новую карточку.

5. После ручного dismissal того же activity ID его поздние события не открывают карточку заново. Dismissal не означает подавление глобального application error UX.

Если терминальная ошибка невидимой activity обнаружена, existing error handling и Git Console остаются источниками информации; приоритет неразрешённой видимой ошибки и отсутствие ложного success соблюдаются. Не строить мини-очередь или полноценный список активности внутри карточки.

### 6.2. Clone и иные существующие operation dialogs

**Clone обязательно интегрировать** с уже существующим `ContentDialog` (`MainPage.RepositoryCloning.cs`): в режиме On в области его прогресса показывать reusable `GitCommandFeedbackView` c Git CLI и live output; при Off сохранять существующую разметку/UX. Не отображать дополнительный root popup для Clone той же invocation. Не менять доступность URL/target inputs во время клонирования, ownership кнопки Cancel и правила закрытия диалога. Не интерпретировать закрытие компактного блока как отмену Clone.

Clone workflow после `git clone` может ещё открывать склонированный репозиторий. Successful Git CLI означает только успешный clone, тогда как ошибка последующего `SwitchRepositoryCoreAsync` должна остаться видимой через **существующее** сообщение `Repository cloned, but could not be opened` (с локальным путём). Не заменять его misleading success. При успешном Clone текущий `ContentDialog` может закрыться в рамках штатного перехода к открытию репозитория **без искусственного ожидания заданного интервала автозакрытия**: правило floating auto-close не задерживает lifecycle родительского диалога.

Для других workflows с уже существующим progress/confirmation dialog сначала оценить, не скрывается ли floating card за modal dialog и не возникает ли конкурирующее окно. Встраивать общий компонент или применять fallback только там, где это необходимо; не переписывать существующую operation orchestration в объёме этой задачи.

Если операция состоит из нескольких Git invocations, каждая User activity самостоятельна; **не создавать составную модель** прогресса workflow. Выполнение Internal-запросов в её составе не создаёт отдельного окна.

### 6.3. Смена репозитория и shutdown

- Activity привязана к её собственным `ActivityId` и исходному `WorkingDirectory`, **никогда** не перепривязывается к выбранному позже репозиторию. Старый event не обновляет feedback другой activity.

- Root compact owner живёт на уровне `MainPage` и не зависит от `RepositoryWorkspace.Visibility`; после switch остаётся валидным только для фактически продолжающей выполняться команды по её ID и корректного UI host.

- При уходе со стартового экрана, смене layout или resizing — избегать dangling XAML references и попадания поверх недоступных controls.

- Во время shutdown отменить таймеры, подписки и UI queue updates; текущие гарантии завершения/отмены mutating operations сохранить без изменений.

## 7. Архитектура

### 7.1. Ownership и границы

Предпочтительная структура:

- `GitCommandFeedbackCoordinator` в **`CSharpGit.Presentation.Core`** (без Uno): state machine, выбор activity, settings snapshots, show-delay, auto-close, dismissal, routing/resync, bounded preview и generation guards. Использовать `IUiDispatcher` или нейтральный scheduler/time abstraction из Core для тестируемых переходов.

- `GitCommandFeedbackView` в **`CSharpGit.Presentation`**: чистый compact Uno/XAML UserControl, получает подготовленный presentation model, emitting `CopyRequested`, `OpenConsoleRequested(activityId)`, `HideRequested`. Нет процесса и Git service.

- `MainPage` / host adapter в **`CSharpGit.Presentation`**: показывает/скрывает модальный overlay в `RootLayout`, открывает Git Console, встраивает тот же view в Clone operation dialog, диспетчеризует UI.

- `GitCommandActivityHistory` в Application остаётся источником session activity; `GitCommandExecutor` в Git — единственным владельцем процесса.

Имена классов — рекомендация. Не создавать второй процессный runner, event bus, persistent history или новый service, дублирующий `IGitCommandActivitySource`.

### 7.2. State model

Для тестирования явно представлять минимум:

- `ActivityId`, original source/owner (floating/embedded), `DisplayCommand`;

- `Status`, `ExitCode?`, `StartedAt`/`Duration`;

- `PreviewText`, `PreviewTruncated`, `OutputAvailable`, active/terminal flags;

- `IsVisible`, `IsDismissed`, `IsHovered`, `HasInteractionFocus`;

- show-delay and remaining auto-close delay, generation token;

- `CanOpenExactConsoleActivity` (determined by current source membership, not an assumption).

Rendering, text selection, XAML brushes and user actions остаются в View. Ключи = immutable GUID, никогда индекс history collection.

### 7.3. Event delivery / UI threads

`IGitCommandActivitySource.Changed` может приходить с фонового потока. Нельзя выполнять XAML property mutations вне dispatcher. Не рассчитывать, что queued callbacks от разных invocations будут приходить в UI в идеальном lifecycle order: проверять ID, generation и terminal-state guards. Не производить полную перестройку Git Console или UI state после каждого чанка.

Избежать гонки между подпиской и первым snapshot: подписаться на source один раз на host lifecycle (или при включении), затем сделать корректный targeted reconciliation, **не** пропуская случившиеся события и **не** повторно добавляя output. Удалять подписки при выключении/удалении host. При settings changes обновлять committed values на UI dispatcher.

### 7.4. Активная activity и лимит 100

**Выявленная проблема реализации:** текущая `GitCommandActivityHistory.Started` вытесняет oldest activity и удаляет её из `_byId` даже если она ещё `Running`; после этого `OutputReceived` и `Finish` её не найдут. Новая UI-фича не должна делать эту проблему незаметной.

Нормативная стратегия для v1:

1. **Сохранить максимум 100 записей в обычной истории Git Console** и её порядок newest-first по IDD-0022. Лимит не становится настройкой.

2. Разделить индекс отображаемой history (макс. 100) и **временное владение ещё running process activities** внутри существующего `GitCommandActivityHistory`, без нового независимого collector. Вытесненная работающая activity может продолжать получать output/terminal state и быть доступна `Get(id)` до её завершения. После terminal state такую detached activity удалить, не возвращая автоматически в 100-record history и не сохраняя на всю session.

3. Количество временных running states ограничено **фактически незавершёнными Git invocations**, без дополнительного безусловного retention для completed events. Каждый output stream соблюдает existing 1 MiB capture limit. Обеспечить cleanup даже при cancellation/failed execution/host shutdown; не плодить таймеры для каждой внутренней команды.

4. Если selected activity вытеснена из 100-record history, **Git Console не обязана показывать её как history row**; переход к точной записи может быть недоступен. UI сообщает об этом честно (§5.8), не подменяя её другой. Это исключение должно быть покрыто тестом.

5. Не изменять внешние Git application results или parser input. Изменение lifetime activity state внутри существующего collector допускается только для устранения потери lifecycle/diagnostics активной invocation.

### 7.5. Память и производительность

- UI compact preview: последние **32 KiB UTF-8 байт безопасного отображаемого текста** (trimming по границам логических строк/Unicode scalar values); bounded pending queue с ограниченным размером; duration display обновлять редко (например, раз в секунду) только пока текущая activity Running и visible.

- Output changes — batching \~75–100 мс; не перерисовывать всю историю Console, не создавать allocation proportional to entire session history при каждом chunk.

- Если output идёт быстрее UI, агрегировать/сбрасывать **только presentation preview**, не изменяя raw/captured Git stdout/stderr или machine-readable parsing. Для актуальной `\r` progress line не допускать безлимитного роста.

- В Off mode — отсутствие compact view listeners/timers и существенной дополнительной обработки. Расширение in-flight tracking в общей истории не должно ухудшать нормальный bounded history path.

- При закрытой Console её существующее правило `no visual live updates` сохраняется.

## 9. Нефункциональные требования

**Поведение и совместимость:** Off mode эквивалентен текущему приложению. Включение никак не изменяет arguments, prompts, Git environment, cancellation, auth, git progress policy, mutation gates и порядок application-level refresh. Не менять публичные results Git services ради UI.

**Security:** `DisplayCommand` и `Output` только из существующего sanitized activity source; не брать исходные `ProcessStartInfo.Arguments`, raw stdout/stderr или environment. Sensitive invocations с intentionally omitted diagnostics так же скрыты в компактном preview. Tooltip, clipboard, error text и invisible view state не должны раскрывать URL credentials, auth headers, tokens/passwords. Escaping IDD-0034 применять и к resync, и к live chunks; никаких literal NUL/ANSI controls в XAML. Маскирование `GitCommandFormatter` и stream sanitizer сохраняют authority; UI не пытается восстановить скрытые аргументы.

**Accessibility:** status текстом и icon, controls с keyboard navigation и доступными именами; appearance не крадёт focus; содержимое не обрезается на масштабированных дисплеях; reasonable min size и High Contrast/Light/Dark в рамках Fluent capabilities.

**Платформы:** Windows + macOS desktop; не использовать Win32-only popup/input hacks. Проверять реальное поведение Uno/Skia `ContentDialog`, overlay, pointer/focus и TextBox на обеих платформах.

## 10. Не входит в задачу

- Полноценный Git log viewer, поиск, фильтрация, export, ANSI/VT terminal emulator.

- Ввод произвольных CLI-команд, retry/run again, script editor.

- Постоянная история действий внутри карточки или история между запусками.

- Процентное определение Git progress и нормализация текстового stderr в структурированные progress phases.

- Универсальная отмена Git процесса из compact view.

- Настраиваемая длительность автозакрытия.

- Полноценная модель дерева составных пользовательских операций.

- Дублирующий Git execution mechanism, collector или settings store.

- Изменение семантики бизнес-операций, workflow locks, prompt handling или UI ошибок.

## 11. Проверка и тестирование

### 11.1. Settings / compatibility

- Новые поля `false` в новом/legacy/неполном JSON; сохранение между запусками; уже существующий `GitConsoleAutoOpenMode` не изменяется.

- При выключенном mode прежние `Always`, `OnErrors`, `Never`, status bar и ручное открытие Console работают побайтно/поведенчески как раньше.

- Live settings change не требует restart; Off hides view без process cancel, On не раскрывает историю ретроспективно; save failure откатывает переключатель.

- `IDiagnosticsSettings.Changed` может приходить с background thread и из concurrent settings updates.

### 11.2. Lifecycle / race

- Started(User) vs Started(Internal); 150ms show delay; быстрые Success/Failure; настраиваемый интервал (по умолчанию 5 секунд) **от видимого финального состояния**.

- Отмена до фактического показа; Cancelled/Failed без auto-close; неизвестный exit code; missing Git executable перед `Process.Start`.

- Отдельно post-start non-cancellation exception не должен называться Cancelled.

- Start/Output/Completed UI queue race; Output до отрисовки Started; resync при `OutputRequiresResync`; queued output после terminal event; поздний event старой activity после новой.

- Hide running не останавливает процесс, не reopens при Completed; новая User invocation может показываться.

- Режим переключён Off в процессе выполнения; host dispose/shutdown при pending timers/output.

### 11.3. Auto-close / UI interaction

- Success остается при Off; при On скрывается после заданного интервала видимости terminal status (по умолчанию 5 секунд, 0 — немедленно).

- Hover и focus **приостанавливают остаток**, removal of hover/focus продолжает; new activity отменяет previous timer.

- Terminal Error sticky приоритетнее нового Success/Running; explicit dismissal разрешает следующую активность, не смешивает IDs.

- Git Console уже вручную открыта: compact mode не закрывает её, не сбрасывает selection без пользовательского действия; manual open по exact ID.

- Модальный overlay перекрывает рабочую область и status bar и блокирует клики вне карточки; явное открытие Git Console скрывает overlay.

### 11.4. Output / privacy / bounded memory

- stdout/stderr по кускам; `\r`, `\r\n`, chunk split at `\r`, UTF-8/Unicode, tabs/newlines, NUL и другие control chars.

- Credentials/token/Authorization redaction на stream boundaries и в copied command/tooltip; intentional diagnostics suppression.

- Combined-stream preview без гарантии global ordering; корректный recent-output marker при 32 KiB; `[output truncated]` остаётся независимым capture marker.

- 1 MiB per stream existing bounded capture; при непрерывном progress UI не увеличивает память без ограничений.

- При ручном scroll up не перескакивать вниз; при возврате к tail auto-follow.

- Reopening/selecting Console по конкретному ID; при вытесненной записи не выбирать чужую.

### 11.5. History eviction / concurrency

- Запустить >100 invocations, пока более старая User activity ещё Running: она не должна терять Output/terminal status в collector, даже если удалена из 100-row history.

- После её завершения detached state освобождается; history остаётся <=100.

- Несколько User invocations одновременно, overlapping Internal events, последовательные короткие commands; карточка всегда соответствует одному ActivityId и deterministic policy §6.1.

- Переход с репозитория A на B, activity события A не подменяют B; создание Clone без открытого репозитория; зафиксированное изменение root layout.

### 11.6. Manual smoke / integration

- На Windows и macOS проверить `Fetch`, `Pull`, `Push`, `Commit`, `Checkout`, `Clone`, git invocation failure, no-output и long-running progress.

- Для Clone отдельно: Off mode прежний ContentDialog, On mode embedded command+output; Cancel штатно останавливает clone, Hide compact UI не останавливает; успешный Git clone + последующий failure открытия репозитория выводит прежнюю осмысленную ошибку.

- Пройти Light/Dark, scaling, resize, small window, page without repo, expanded Git Console, existing confirmation dialogs и shutdown.

- Выполнить unit tests нейтрального coordinator через controlled clock/scheduler **без реальных задержек по 5 секунд**, contract/integration Git activity и settings tests, обе desktop сборки.

## 12. Критерии приёмки

1. По умолчанию feedback выключен; выключенная функция не меняет UX или auto-open Git Console.

2. Обе настройки доступны в Diagnostics, сохранены в одном settings JSON и применяются без перезапуска.

3. User CLI activity отображается в небольшом ненавязчивом view (root modal или embedded Clone); Internal activity не создаёт автоматического compact view.

4. Фактическая CLI invocation выделена и безопасно копируется; при sensitive аргументах действует existing redaction.

5. В течение длительного выполнения видны поступающие stdout/stderr и перезаписываемая `\r` progress line, с bounded preview.

6. Известные CLI outcome, duration и exit code отображаются правильно; failure после запуска не маскируется как пользовательская cancellation.

7. Быстрая команда не мигает Running; результат модального feedback остаётся видимым заданное время (по умолчанию 5 секунд) от появления успешного terminal status при auto-close. Embedded Clone следует lifecycle существующего родительского диалога и не задерживает открытие репозитория.

8. Failed/Cancelled сами не скрываются; hover/focus приостанавливает оставшуюся задержку auto-close.

9. Закрытие компактного представления не останавливает Git и не приводит к повторному появлению того же завершённого activity.

10. `Open Git Console` адресует точный ActivityId или честно сообщает, что запись вытеснена; никогда не подменяет её другой записью.

11. Automatic Git Console open для activity, обслуживаемой compact view, подавляется без влияния на ручное открытие или application error UX; если feedback недоступен, работает прежний fallback.

12. Concurrent events/commands не смешивают output и не закрывают чужой view; непрочитанная ошибка не исчезает из-за последующего успешного события.

13. Existing Clone ContentDialog сохраняет busy/cancel/closing ownership, получает embedded reusable feedback в режиме On и не порождает второй popup.

14. История Git Console не превышает 100, но текущая вытесненная running invocation не теряет lifecycle events до завершения; временный detached state затем освобождается.

15. Security/presentation sanitization, parser semantics, JSON compatibility, Git workflows и поддержка Windows/macOS сохранены; тесты и сборки проходят.

## 13. Порядок выполнения

1. **Settings + contract:** расширить Diagnostics facet, единый persistence store, UI + compatibility tests.

2. **Core state machine:** deterministic selection, dismissal, timers с injectable scheduler, bounded preview и tests.

3. **History lifecycle fix:** отделить running activity lifetime от 100-row history, завершить cleanup/test >100 scenario; узко исправить post-start exception status.

4. **Reusable Uno view:** компактный общий UserControl, root modal overlay в `RootLayout`, focus/accessibility/styles.

5. **Activity wiring:** Started/Output/Completed, initial 150ms, throttle/resync, output encoding, memory guards.

6. **Console integration:** exact-ID manual open, ID-aware auto-open suppression/fallback, сохранить старое поведение при Off.

7. **Clone integration:** embedded view в текущем `ContentDialog` без изменения cancel/close/launch/orchestration.

8. **Verification:** unit + integration + contract tests, Windows/macOS build + interactive smoke tests.
