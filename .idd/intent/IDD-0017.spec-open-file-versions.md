# IDD-0017 — Open diff file versions

## Status

Current product intent.

## Purpose

CSharpGit lets a user move naturally from a displayed file diff to either side of that diff, or to the corresponding real file in the current working tree.

The capability applies to commit `Changes` and Working Tree diffs.

## Core invariant

`Open original` means the exact OLD side of the diff currently represented by CSharpGit.

`Open changed` means the exact NEW side of that diff.

The commands must not independently invent a different baseline. When diff semantics evolve, file-opening semantics evolve with them.

## Commit Changes

The compact diff header exposes `Original`, `Changed`, and `Reveal` actions without restoring the removed selected-file-name row or reducing useful diff height.

The Changed-files context menu exposes the same actions. Folder nodes do not expose file actions.

Double-click opens the natural existing side: normally Changed; for a deletion, Original. It never executes an unavailable side.

Commit diff semantics use the same first-parent baseline as the displayed normal commit diff. A root commit has no Original side.

Change semantics are:

- Modified: baseline path -> commit path;
- Added: Original unavailable, Changed is commit blob;
- Deleted: Original is baseline blob, Changed unavailable;
- Renamed: Original is old baseline path, Changed is new commit path;
- Copied: Original is source/baseline path, Changed is copied commit path.

Rename/copy metadata is resolved by the Git layer with NUL-delimited output. Presentation must not infer old paths from names.

Merge commits use the same baseline selected by the normal displayed diff; current behavior is first parent. This feature does not add merge-parent selection UI.

## Working Tree

Working Tree actions always follow the pair actually shown by the existing Working Tree diff surface:

- unstaged diff: `index -> working copy`;
- staged diff: `HEAD -> index`.

This deliberately preserves IDD-0005 staged/unstaged semantics. If a file has both staged and unstaged changes, selecting each row opens the corresponding pair rather than collapsing both views into `HEAD -> working copy`.

Untracked files have no Original side. Deleted files have no Changed side. `Open changed` opens the real editable working-copy file whenever Changed is the working-copy side; Git snapshots are never substituted for that case.

## Historical and index snapshots

Git-backed versions are materialized outside the repository under an application temp/cache root.

Snapshot extraction is binary-safe: raw Git blob stdout is copied directly to a file stream without conversion through `string` or text writers.

Materialization must:

- preserve blob bytes exactly;
- preserve a safe form of the source filename/extension when possible;
- derive cache identity from repository identity, revision/index identity, blob/path, and side;
- prevent path traversal and filename collisions;
- write to a unique temporary file first and atomically move the completed file into cache;
- remove incomplete temporary output after failure or cancellation;
- best-effort mark completed historical/index snapshots read-only;
- never checkout, mutate HEAD, mutate the index, or write to the working tree;
- best-effort clean old cache files without failing application shutdown/startup.

Symbolic-link snapshots, gitlinks/submodules, and other unsupported Git entry types are unavailable in the first version and show an explanatory reason rather than being materialized as regular files.

## Working-copy path safety

Opening a real working-copy file requires canonical path validation against the canonical repository working directory.

Relative traversal and absolute Git paths are rejected. Opening through a directory symbolic link, Windows junction, or other reparse point is rejected so a repository path cannot cause CSharpGit to launch an arbitrary file outside repository context.

Reveal may reveal a final link entry, but it must not traverse a linked parent directory outside the repository.

The file is revalidated at execution time because repository state can change after UI command state was computed.

## Desktop shell boundary

External application launching and file-manager reveal are application/platform capabilities, not Git or XAML concerns.

All new open/reveal flows use `IDesktopShellService` (or its semantic equivalent). Existing manual conflict opening uses the same boundary.

Reveal is platform-specific:

- Windows selects the real file in Explorer;
- macOS reveals the real file in Finder;
- Linux best-effort opens the containing directory.

Commit-history Reveal always targets the corresponding current working-tree path. It never reveals an internal materialized snapshot.

## Command state and errors

Header buttons, context menu, and double-click consume one resolved pair of side descriptors. Availability rules are not duplicated in independent UI handlers.

Unavailable actions provide a reason such as file-added, file-deleted, unsupported entry, or current working-tree path absent.

Every operation revalidates immediately before opening/materializing/revealing. Failures become short user-facing errors; raw stack traces are not the primary UI message. Cancellation is not reported as a generic failure.

## Verification

Automated coverage should include at least:

- Modified, Added, Deleted and root commits;
- rename old/new paths and copy metadata;
- merge first-parent baseline;
- byte-for-byte binary snapshots;
- Unicode and space-containing paths;
- repeated snapshot materialization;
- staged `HEAD -> index` and unstaged `index -> working copy` for one file;
- untracked and Working Tree deleted files;
- traversal and repository-root escape rejection, plus symlink/reparse-point escape where supported;
- UI wiring for header/context-menu/double-click sharing the same file-version service;
- shell launching behind an abstraction rather than real external-app launching in CI.

## Out of scope

This feature does not add an embedded editor, preferred-editor settings, merge-parent selection, a separate `Open staged version` command, checkout/restore of historical files, writable historical snapshots, submodule opening, or historical filesystem-symlink creation.
