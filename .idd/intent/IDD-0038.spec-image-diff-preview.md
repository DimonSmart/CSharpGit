# Image Diff Preview

## Intent

CSharpGit treats supported raster images as a first-class previewable diff type rather than as unknown binary content.

A selected file diff has one of three semantic presentations: text, supported image, or other binary. Binary status means only that text diff is unavailable; it does not itself determine the final renderer.

Image comparison is deliberately deterministic and metadata-based. It shows the exact Original and Changed versions and explains only changes that can be derived reliably from image metadata. It does not interpret pixels.

## Behavior

### Commit Changes

For a binary file selected in Commit Changes, CSharpGit resolves the exact Original/Changed pair using the same file-version semantics as existing file actions. Supported images are shown as an image comparison instead of the generic binary message.

Commit parent selection, root commits, renames, copies, and existing merge semantics remain owned by the shared file-version abstraction. Image diff does not reproduce those rules.

### Working Tree

Image comparison supports both working-tree deltas:

- unstaged: index → working copy;
- staged: HEAD → index.

The pair is resolved by the same working-tree file-version abstraction used by existing Original/Changed actions.

### Image comparison

When both sides exist and are supported images, Original and Changed are displayed with equal visual role. Images use uniform scaling and are not cropped.

When horizontal space is insufficient, the comparison may stack vertically rather than shrinking both sides into unreadable thumbnails. The responsive decision is based on the available diff host width.

For each readable image side the presentation includes actual format, width × height, and file size.

When reliably observable, the summary reports:

- resized dimensions;
- swapped non-square dimensions and, separately, a cautious `Possible 90° rotation` hint;
- actual format changes;
- file-size changes, including an approximate percentage relative to Original when defined.

If binary content changed while the compared required metadata remains the same, the summary states that content changed while dimensions, format, and file size are unchanged.

No claim is made about crop, colors, brightness, objects, text, faces, backgrounds, or other pixel-level meaning.

### Added and deleted images

An added image displays an explicit missing Original side and the Changed image.

A deleted image displays the Original image and an explicit missing Changed side.

Missing sides are semantic states, not generated transparent or empty bitmaps.

### Unsupported and failed previews

For modified/renamed/copied binary content where an existing side is not a supported image, the surface falls back to the ordinary binary presentation.

A supported image whose pixels cannot be rendered does not force the whole comparison back to generic binary. That side reports `Preview unavailable`, retains reliable metadata, and the other image side remains usable.

Image-preview failures are non-critical and do not produce modal errors.

## Durable Architecture And Constraints

Image diff reuses the existing exact file-version abstraction. Presentation does not issue ad-hoc `git show`, `git cat-file`, or `git diff` commands.

Historical/index versions are materialized through the existing file-version service. A WorkingCopy version is resolved through the safe repository-path service and is not passed to historical materialization.

Single-image preview and image diff share one content-based metadata-reading implementation for supported image formats. PNG and JPEG are required. Format is determined from actual content, not extension.

Metadata reading is bounded and does not require full bitmap decoding. The compressed image limit and decoded-image safety limit are separate. Excessive dimensions or pixel count prevent rendering, and pixel-count arithmetic is overflow-safe.

Image diff is lazy. It is prepared only for the selected binary file; images are not materialized, inspected, or decoded for every changed file in advance. Decoded bitmaps are not stored in diff caches.

Commit image requests are invalidated by repository, selected commit, selected path, or diff-context changes. Working-tree image loading participates in the existing working-tree cancellation/generation lifecycle. A stale asynchronous result must never replace the current renderer.

The diff surface has an explicit final presentation state so text, image, loading, other-binary, and unavailable/no-change presentations are mutually exclusive. The generic binary InfoBar is not driven directly by the raw binary flag.

Existing Original, Changed, external Diff tool, and Reveal actions retain their semantics regardless of the built-in renderer.

The same architecture path is used on Windows and macOS; image metadata parsing does not require platform-specific code or a new direct SkiaSharp dependency.

## Non-Goals

This intent does not include:

- pixel-by-pixel diff, heatmap, overlay, slider or blink comparison;
- perceptual hashes or similarity scoring;
- AI, OCR, object recognition or semantic image description;
- automatic crop, palette, brightness, background, face or text analysis;
- image editing;
- full zoom/pan image viewing;
- animated GIF comparison;
- SVG, PDF or video preview.

## Acceptance Criteria

- PNG/JPEG single preview continues to work and shows format, dimensions and file size.
- Supported PNG/JPEG binary changes use image comparison in Commit Changes, staged changes and unstaged changes.
- Supported content is detected independently of extension, and invalid image content is rejected safely.
- Added/deleted images use explicit missing-side states.
- Dimension, format and file-size changes are reported only from reliable metadata.
- Swapped non-square dimensions may produce a possible-rotation hint but never a guaranteed rotation claim.
- Unsupported binary content retains the existing generic binary fallback.
- Text diff behavior is unchanged.
- Image comparison and generic binary fallback are never visible simultaneously.
- WorkingCopy is resolved through the repository path boundary; Git snapshots use existing materialization.
- Oversized compressed or decoded images are not passed to the bitmap renderer.
- Corrupt images and decoder failures do not crash the diff surface.
- Stale commit or working-tree image results cannot publish after selection/context changes.
- Existing Original, Changed, Diff tool and Reveal actions continue to work.

## Verification

Automated coverage verifies valid PNG/JPEG content detection and metadata, unrelated extensions, invalid/corrupt headers, resize and swapped-dimension comparison, file-size increase/decrease, format changes, unchanged required metadata, added/deleted states, unsupported binary fallback, compressed/decode safety, pixel-count overflow safety, explicit renderer selection, staged/unstaged/commit integration, safe WorkingCopy versus GitSnapshot resolution, shared metadata reading, and stale-publication guards.

## Shared Diff Surface Integration

Image states participate in the generalized diff-surface state machine used by historical Changes and Working Tree. `LoadingImage`, `Image` and `OtherBinary` remain distinct from text loading/text, no-textual-patch, disappeared Working Tree delta and error states.

Changing away from an image invalidates stale image publication and clears the image host as before. Returning to text uses the shared semantic viewport rule: the new text diff starts at `(0,0)`. This integration does not change image comparison, metadata, bounded-loading, cancellation, file-version resolution or supported-format semantics defined by this intent.
