# Кроссплатформенный Git GUI клиент

## 1. Цель продукта

Создать современный кроссплатформенный desktop GUI-клиент для Git, вдохновлённый Git Extensions.

Git Extensions используется как:

- ориентир по структуре интерфейса;
- ориентир по основным пользовательским сценариям;
- ориентир по Git workflows;
- ориентир по тому, какая информация должна быть доступна пользователю;
- основной behavioral reference для сценариев, не определённых настоящим Intent достаточно подробно.

Приложение не должно быть буквальным клоном Git Extensions.

Pixel-perfect воспроизведение Git Extensions не требуется. Если существующее поведение или UI Git Extensions кажется нелогичным, устаревшим или избыточным, допускается выбрать более простой и современный вариант при сохранении полезной Git semantics.

Дополнительная цель проекта — проверить возможность создания достаточно сложного desktop-приложения преимущественно средствами IDD Factory / Codex.

---

# 2. Основные продуктовые принципы

## 2.1. Git является source of truth

Приложение не должно создавать собственную альтернативную модель состояния repository, которая может расходиться с Git.

Состояние:

- commits;
- branches;
- tags;
- remotes;
- working tree;
- index;
- stash;
- repository configuration;
- незавершённых Git operations

должно определяться фактическим состоянием Git repository.

Допускается кэширование данных для UI и производительности, но кэш не является authoritative state.

После операций, способных изменить repository, приложение должно получать актуальное состояние из Git, а не предполагать результат на основании только собственного предыдущего состояния.

## 2.2. Git Extensions как behavioral reference

Если пользовательский сценарий или Git behavior не определён настоящим Intent достаточно точно, при реализации следует изучить соответствующее поведение Git Extensions и использовать его как исходный вариант.

Приоритет правил:

1. explicit requirements настоящего Intent;
2. фактическая Git semantics;
3. behavior Git Extensions как reference;
4. implementation decision.

Git Extensions является ориентиром прежде всего по:

- semantics;
- workflow;
- доступным пользователю действиям;
- составу отображаемой информации.

Не требуется копировать:

- визуальный layout;
- конкретные dialogs;
- внутреннюю архитектуру;
- implementation details Git Extensions.

Существенное отступление от поведения Git Extensions в неописанном Intent пользовательском сценарии должно быть осознанным решением, а не случайным следствием реализации.

## 2.3. Desktop-first

Это desktop-приложение.

Основные поддерживаемые платформы:

- Windows;
- macOS.

Linux поддерживается в режиме best effort на начальном этапе.

## 2.4. Общий UI

На всех платформах должна использоваться одна и та же основная иерархия Views и одинаковая продуктовая модель.

Не требуется pixel-perfect идентичность Windows, macOS и Linux.

Platform-specific UI следует избегать.

Платформенный код допустим там, где он действительно необходим для интеграции с ОС, например:

- native dialogs;
- filesystem integration;
- opening files/applications;
- clipboard;
- shell integration;
- platform shortcuts.

# 3. Технологический стек

Обязательный стек:

- .NET 10 LTS;
- Uno Platform;
- Skia Desktop;
- XAML;
- Fluent design system;
- MVVM.

Использовать Skia Desktop как desktop rendering target.

Не создавать отдельные платформенные реализации UI без необходимости.

Предпочитать стандартные Uno controls собственным controls.

Custom controls и custom drawing использовать только там, где обычные controls не подходят.

Основной ожидаемый пример custom drawing:

- commit graph.

UI-логика должна быть отделена от Git/domain logic посредством MVVM и соответствующих application/domain services.

---

# 4. Проверка UI агентами

Codex при разработке UI должен, когда это практически возможно, использовать Uno MCP / App MCP для проверки изменений на реально запущенном приложении.

Недостаточно считать XAML корректным только потому, что проект компилируется.

Для значимых UI-изменений желательно проверять:

- фактическое расположение controls;
- sizing;
- scrolling;
- clipping;
- состояние controls;
- отображение реальных данных;
- основные пользовательские сценарии;
- disabled/enabled состояния actions;
- поведение при resize.

---

# 5. Работа с repositories

## 5.1. MVP

В первой версии пользователь работает с уже существующим локальным Git repository.

Основной сценарий:

1. запустить приложение;
2. выбрать локальную папку;
3. открыть находящийся в ней Git repository.

Приложение должно корректно определять repository также при открытии существующего Git worktree.

## 5.2. Не требуется для первой версии

MVP не обязан поддерживать:

- Clone;
- Init.

При этом архитектура не должна препятствовать добавлению этих функций позднее.

---

# 6. Модель приложения

Один экземпляр приложения работает с одним открытым repository.

Не требуется система вкладок с несколькими repositories внутри одного окна.

Пользователь может одновременно запустить несколько экземпляров приложения и открыть разные repositories.

Не требуется централизованная блокировка, запрещающая несколько экземпляров приложения.

Несколько экземпляров приложения могут наблюдать изменения одного repository. В таком случае фактическое состояние Git остаётся source of truth.

---

# 7. Главное окно

Главное окно должно давать быстрый доступ как минимум к следующим областям:

- commit history;
- commit graph;
- branches / refs;
- working tree changes;
- staged changes;
- commit details;
- diff;
- основные Git actions.

Интерфейс может быть близок по организации к Git Extensions, если это удобно, но не должен копировать его механически.

Пользователь должен иметь возможность изменять размеры основных панелей там, где это необходимо для комфортной работы.

---

# 8. Commit history

Центральным элементом приложения является история commits.

Для commit должны быть доступны как минимум:

- graph;
- commit message;
- author;
- date/time;
- commit hash;
- refs, относящиеся к commit.

История должна показывать topology Git history, включая:

- обычную последовательность commits;
- branches;
- merges.

## 8.1. Scope истории

Commit history должен иметь явно определённый scope.

Пользователь должен иметь возможность как минимум переключаться между:

- history текущей branch;
- history всех доступных branches/refs.

UI должен явно показывать текущий scope истории.

По умолчанию предпочтительно отображать историю всех доступных refs, аналогично классическому Git GUI workflow, если это не создаёт существенных проблем производительности или usability.

## 8.2. Columns

История должна поддерживать основные колонки.

Набор и/или отображение колонок желательно сделать configurable.

Не следует жёстко связывать application logic с конкретным фиксированным layout таблицы.

## 8.3. Loading

Большие repositories не должны требовать загрузки всей истории перед отображением UI.

История должна поддерживать incremental loading / lazy loading.

## 8.4. Filtering

Должна существовать возможность фильтрации/поиска истории по основным пользовательским критериям.

Конкретный расширенный query language для первой версии не требуется.

---

# 9. Commit graph

Commit graph должен визуально показывать Git topology.

Он должен корректно отображать:

- последовательные commits;
- создание branch;
- merge;
- несколько одновременно существующих branches.

Для graph допускается custom drawing, поскольку стандартные controls могут быть для этого недостаточны.

Graph должен оставаться согласованным с соответствующими строками commit history.

Graph не должен содержать собственную независимую модель topology, способную расходиться с данными Git.

---

# 10. Commit details

При выборе commit пользователь должен видеть подробную информацию о нём.

Как минимум:

- full commit message;
- author;
- date/time;
- hash;
- parent commit(s);
- refs;
- список изменённых файлов.

При выборе файла должна быть возможность посмотреть соответствующее изменение.

---

# 11. Diff viewer

Должен существовать встроенный просмотр diff.

Основной формат:

- unified diff.

Diff должен различать как минимум:

- added lines;
- removed lines;
- context.

Для выбранного изменения пользователь должен иметь возможность посмотреть содержимое соответствующего файла, когда это применимо.

Встроенный diff viewer является основным способом просмотра обычных textual changes.

Поддержка внешнего diff tool может быть добавлена, но не является обязательным условием MVP, если она не требуется для conflict workflow.

---

# 12. Binary files

Приложение не обязано строить текстовый diff для бинарных файлов.

Если файл определяется как binary, UI должен корректно сообщить пользователю, что содержимое является binary data, вместо попытки показать его как текст.

Специализированные viewers для изображений, архивов и других бинарных форматов в MVP не требуются.

---

# 13. Working tree

Приложение должно отображать текущее состояние working tree и Git index.

Необходимо корректно отражать как минимум:

- modified;
- added;
- untracked;
- deleted;
- renamed;
- conflicted.

Staged и unstaged являются характеристиками изменений относительно разных Git states и не должны моделироваться как взаимоисключающие состояния файла.

Один и тот же файл может одновременно содержать:

- staged changes;
- дополнительные unstaged changes.

UI должен позволять пользователю это однозначно понять.

Изменение файла вне приложения должно впоследствии отражаться в UI.

---

# 14. External changes и Refresh

Repository может изменяться не только самим Git-клиентом:

- CLI;
- IDE;
- другой Git GUI;
- filesystem operations;
- другой экземпляр приложения.

Приложение должно уметь обновлять своё состояние при внешних изменениях.

Предпочтительно автоматическое обновление.

Также должна существовать явная команда:

**Refresh**

Пользователь не должен быть вынужден закрывать и заново открывать repository после внешнего изменения.

Refresh должен перечитывать фактическое состояние Git, включая незавершённые Git operations.

---

# 15. Staging

MVP работает на уровне целого файла.

Поддерживаются:

- Stage file;
- Unstage file.

Не требуется в первой версии:

- stage selected hunk;
- stage selected lines;
- partial staging.

Архитектура не должна намеренно препятствовать добавлению partial staging позднее.

Staging является отдельной явной пользовательской операцией.

Другие действия приложения не должны молча изменять index, кроме случаев, где это является неизбежной стандартной частью конкретной Git operation и явно отражено в UI.

---

# 16. Commit

Пользователь должен иметь возможность:

- видеть staged changes, составляющие текущее состояние Git index;
- ввести commit message;
- создать commit из текущего состояния Git index.

Обычный Commit не должен неявно stage или unstage файлы.

Если Git index содержит staged changes, commit создаётся именно из них.

Наличие дополнительных unstaged changes не должно приводить к их автоматическому включению в commit.

## 16.1. Commit при пустом index

Если пользователь инициирует Commit при пустом Git index, но в working tree существуют изменения, приложение должно явно предложить дальнейшее действие.

Минимально должны быть доступны варианты:

- Stage all и продолжить commit;
- вернуться к working tree и самостоятельно выбрать файлы для staging;
- отменить Commit.

Допускается также поддерживать intentional empty commit, если это действие:

- явно отделено от обычного commit;
- требует осознанного выбора пользователя.

Приложение не должно самостоятельно выбирать, какие unstaged files включать в commit.

## 16.2. После commit

После успешного commit UI должен обновить:

- history;
- graph;
- refs;
- working tree;
- index state.

## 16.3. Amend

Должна поддерживаться операция:

- Amend last commit.

UI должен явно показывать пользователю, что выполняется amend, а не обычный новый commit.

Amend должен сохранять реальную Git semantics.

---

# 17. Branches

Приложение должно отображать:

- local branches;
- remote branches.

Необходимы базовые операции с branches, включая:

- checkout/switch;
- создание branch;
- удаление branch, когда Git это позволяет.

Текущая branch должна быть однозначно видна в UI.

---

# 18. Detached HEAD

Приложение должно корректно распознавать и отображать состояние detached HEAD.

Detached HEAD не должен ошибочно отображаться как обычная current branch.

Операции, требующие существования текущей branch, должны учитывать detached HEAD и либо:

- работать согласно Git semantics;
- либо быть недоступными с понятным объяснением.

---

# 19. Tracking branches

Приложение должно понимать связь local branch с upstream/tracking branch.

При работе с remote branch должен поддерживаться нормальный сценарий checkout с созданием соответствующей local tracking branch, когда это необходимо.

Pull по умолчанию должен работать с configured upstream текущей branch.

Push должен использовать стандартную Git configuration.

Если upstream отсутствует и операция требует его указания, UI должен позволить пользователю явно выбрать remote/branch и при необходимости установить upstream.

Приложение не должно молча выбирать произвольный remote branch.

---

# 20. Remotes

Приложение должно отображать настроенные remotes и связанные remote branches.

Для MVP достаточно стандартной модели Git remotes.

Сложный отдельный remote-management subsystem не требуется, если он не нужен для основных операций.

---

# 21. Authentication

Для remote operations приложение должно использовать стандартные Git authentication mechanisms пользователя.

Приложение не должно создавать собственное хранилище:

- passwords;
- access tokens;
- SSH private keys.

Должны нормально работать существующие механизмы Git, насколько это позволяет выбранный integration approach:

- Git credential helpers;
- Git Credential Manager;
- SSH configuration;
- SSH agent;
- другие standard Git authentication mechanisms.

Authentication failures должны отображаться пользователю как понятные ошибки Git.

Полноценный собственный credentials manager в MVP не требуется.

---

# 22. Fetch / Pull / Push

Должны поддерживаться основные remote operations:

- Fetch;
- Pull;
- Push.

Также должна существовать операция:

- Fetch All.

После завершения операции интерфейс должен обновлять соответствующее состояние repository.

Ошибки Git должны отображаться пользователю в понятной форме.

Remote operations не должны блокировать UI thread.

---

# 23. Tags

Приложение должно отображать Git tags.

UI истории должен уметь показывать tag как ref соответствующего commit.

Для первой полноценной версии достаточно чтения и отображения tags.

Не являются обязательными для MVP:

- Create tag;
- Delete tag;
- Push tag;
- отдельный tag-management subsystem.

Эти функции могут быть добавлены позднее.

---

# 24. Stash

Stash входит в функциональность приложения.

Минимально должны поддерживаться:

- создать stash;
- посмотреть список stash entries;
- Apply;
- Pop.

Работа со stash должна быть отдельным понятным пользовательским сценарием.

Расширенные функции stash могут быть добавлены позднее.

---

# 25. Merge

Приложение должно позволять выполнить merge выбранной branch в текущую branch.

Git semantics должны сохраняться, включая применимые случаи:

- fast-forward;
- merge commit;
- отказ Git от операции;
- conflicts.

Приложение не должно самостоятельно эмулировать merge.

При возникновении conflicts repository должен оставаться в реальном состоянии незавершённого merge.

UI должен перейти к соответствующему conflict workflow.

При успешном merge должны обновляться:

- history;
- graph;
- refs;
- working tree;
- index.

---

# 26. Rebase

Приложение должно поддерживать rebase.

В том числе предусматривается interactive rebase.

Для interactive rebase должны быть доступны основные действия:

- pick;
- reword;
- squash;
- fixup;
- drop;
- reorder.

Не требуется копировать UI Git Extensions — можно сделать более простой интерфейс, если семантика Git сохраняется.

При остановке rebase из-за conflicts приложение должно переходить в общий conflict workflow.

---

# 27. Conflicts

Git operations могут привести к conflicts.

Приложение не должно самостоятельно угадывать правильное разрешение conflict.

UI должен явно показывать:

- наличие незавершённой Git operation;
- список конфликтующих файлов;
- состояние каждого conflict;
- доступные для текущей operation действия.

Для конфликтующего файла пользователь должен иметь возможность как минимум:

- выбрать файл;
- увидеть его conflict state;
- открыть файл для ручного редактирования;
- запустить настроенный внешний merge tool;
- stage файл после разрешения conflict;
- выбрать local/current или remote/incoming version там, где это имеет однозначную Git semantics;
- удалить файл или сохранить соответствующую сторону в applicable delete/modify conflicts.

Для текущей Git operation приложение должно предоставлять применимые действия:

- Continue;
- Skip, когда Git operation это поддерживает;
- Abort, когда Git это поддерживает.

## 27.1. Local / Remote / Ours / Theirs

UI должен учитывать, что смысл `ours` и `theirs`, а также local/current и remote/incoming может различаться для merge и rebase.

Приложение не должно механически показывать пользователю `ours/theirs`, если это способно ввести его в заблуждение.

Предпочтительно использовать понятные contextual labels по модели Git Extensions.

## 27.2. Определение resolved state

Приложение не должно считать conflict разрешённым только потому, что:

- внешний editor был открыт;
- mergetool завершил process;
- пользователь закрыл dialog.

После действия приложение должно перечитать реальное состояние Git.

Resolved/unresolved state определяется фактическим состоянием repository и index.

## 27.3. Нестандартные conflict types

Для:

- add/add;
- modify/delete;
- delete/modify;
- binary conflicts;
- других конфликтов, где обычный textual merge недостаточен,

UI должен предоставлять подходящие действия выбора версии, сохранения или удаления по образцу Git Extensions.

Встроенный полноценный graphical three-way merge editor в MVP не требуется.

---

# 28. External merge tool

Приложение должно поддерживать настройку внешнего merge tool для разрешения conflicts.

Пользователь должен иметь возможность настроить как минимум:

- используемый merge tool;
- executable/path, если необходимо;
- command/arguments для запуска.

Следует использовать стандартную Git configuration там, где это практически возможно, вместо создания несовместимого собственного configuration format.

Следует учитывать обычную Git-модель:

- global configuration;
- repository-local configuration.

Допускается:

- predefined configuration для известных merge tools;
- custom tool;
- custom command.

Внешнему tool должны передаваться необходимые representations согласно стандартной Git mergetool semantics, включая применимые:

- BASE;
- LOCAL;
- REMOTE;
- MERGED/result.

## 28.1. Режим Open in `<merge tool>`

Для выбранного конфликтующего файла пользователь должен иметь возможность выполнить:

**Open in `<configured merge tool>`**

Этот режим запускает merge tool только для выбранного conflict.

Он предназначен для сценария, когда пользователь вручную последовательно выбирает конкретные файлы.

## 28.2. Режим Start mergetool

Также должна существовать отдельная операция:

**Start mergetool**

Она запускает стандартный mergetool workflow для repository и позволяет последовательно обработать существующие conflicts.

При использовании Git CLI этот режим естественным образом может использовать стандартный `git mergetool`.

Наличие `Open in <tool>` не заменяет `Start mergetool`, и наоборот.

---

# 29. In-progress Git operations

Состояние незавершённых Git operations не должно существовать только в памяти приложения.

При:

- открытии repository;
- Refresh;
- возвращении приложения в активное состояние;
- завершении внешнего merge tool;
- завершении Git command

приложение должно при необходимости определять фактическое состояние repository.

Как минимум должны восстанавливаться поддерживаемые приложением незавершённые:

- merge;
- rebase.

Если пользователь:

1. начал operation;
2. получил conflicts;
3. закрыл приложение;
4. снова открыл repository,

приложение должно определить существующую незавершённую operation и вернуть пользователя в соответствующий workflow.

Перезапуск приложения не должен приводить к потере возможности:

- продолжить operation;
- разрешить conflicts;
- выполнить Abort.

---

# 30. Destructive working-tree operations

Пользователь должен иметь возможность отказаться от незакоммиченных изменений целого файла.

Минимальная операция:

- Discard file changes.

Discard является destructive operation.

Перед фактической потерей пользовательских изменений требуется explicit confirmation.

Приложение не должно создавать фиктивную модель Undo для discarded changes.

Partial discard не является обязательным для MVP.

---

# 31. Ошибки

Ошибки Git не должны отображаться пользователю только как необработанные exception stack traces.

Пользователь должен получать:

- понятное краткое описание;
- необходимый контекст;
- при необходимости оригинальную диагностическую информацию Git.

Ошибки не следует искусственно скрывать.

Для troubleshooting должна сохраняться возможность увидеть достаточно технической информации.

Отсутствие или неправильная конфигурация внешнего tool должна приводить к понятной диагностике, а не к необработанному exception.

---

# 32. Worktrees

Git worktrees должны корректно поддерживаться как рабочие repositories.

Если пользователь открывает существующий worktree, приложение должно нормально с ним работать.

Желательно также позволять пользователю:

- видеть связанные worktrees;
- открывать существующий worktree.

Для первой версии не обязательны полноценные операции управления worktrees:

- create;
- remove;
- prune;
- advanced worktree management.

Это future functionality.

---

# 33. Configuration

Приложение должно учитывать Git configuration там, где она влияет на выполняемые Git operations.

Не следует создавать собственные дублирующие настройки без причины.

Application-specific настройки допустимы для UI и поведения самого клиента.

Там, где Git уже предоставляет стандартный configuration mechanism, следует предпочитать его.

---

# 34. Git runtime

Конкретный механизм взаимодействия с Git остаётся implementation decision.

Если реализация зависит от установленного Git executable, приложение должно:

- обнаруживать его отсутствие;
- обнаруживать невозможность его запуска;
- показывать понятную диагностику.

Отсутствующий Git runtime не должен приводить к необработанному exception или непонятному состоянию UI.

Не требуется заранее фиксировать конкретную minimum Git version, если такая необходимость не возникла из поддерживаемых функций.

---

# 35. Appearance

Приложение должно поддерживать:

- System;
- Light;
- Dark.

Fluent является основным design system.

Приложение не обязано выглядеть абсолютно одинаково на разных ОС.

---

# 36. Localization

Для первой версии UI приложения:

- English only.

Архитектура не должна специально усложняться ради localization, если она пока не требуется.

---

# 37. Telemetry

В первой версии не требуется telemetry или сбор пользовательской аналитики.

Приложение не должно зависеть от внешней telemetry infrastructure для нормальной работы.

---

# 38. Производительность

Приложение должно оставаться usable на реальных repositories с большой историей.

Особое внимание требуется для:

- commit history;
- commit graph;
- diff;
- repository refresh;
- external filesystem changes.

Не следует предварительно загружать данные, которые не нужны для отображаемого состояния UI.

История должна загружаться incrementally.

Долгие Git operations не должны блокировать UI thread.

---

# 39. Асинхронность и конкурентные операции

Git operations, filesystem operations и загрузка истории должны выполняться без блокировки UI.

UI должен показывать занятость там, где операция занимает заметное время.

Повторное нажатие action не должно случайно запускать несколько одинаковых или конфликтующих операций.

В пределах одного repository приложение не должно параллельно запускать несовместимые mutating Git operations.

Пока выполняется mutating operation:

- несовместимые actions должны быть disabled;
- либо попытка запуска должна быть корректно отклонена.

Read-only operations могут выполняться параллельно, если это безопасно.

---

# 40. Separation of concerns

Git/domain logic не должна находиться непосредственно в code-behind Views.

Ожидаемое разделение:

- Views;
- ViewModels;
- application/domain services;
- Git integration;
- infrastructure/platform integration.

ViewModels не должны превращаться в обёртки над command-line strings.

Git-specific execution details должны быть скрыты за соответствующим service layer.

---

# 41. Git integration

Конкретный низкоуровневый механизм взаимодействия с Git может быть выбран при реализации, если он соответствует требованиям продукта.

Критические требования:

- поддерживать необходимую Git semantics;
- корректно работать с реальными repositories;
- не создавать собственную несовместимую модель Git;
- предоставлять достаточную диагностику ошибок.

Выбор между:

- Git CLI;
- подходящей библиотекой;
- комбинацией этих подходов

является implementation decision, если продуктовые требования от этого не меняются.

---

# 42. Undo и destructive operations

Приложение не должно создавать собственную фиктивную модель Undo для операций, которые Git сам по себе не предоставляет как безопасный Undo.

Потенциально destructive operations должны быть явно обозначены.

Там, где риск потери данных существенен, UI должен требовать осознанного действия пользователя.

---

# 43. Пользовательский ввод при закрытии

При закрытии repository или приложения UI не должен молча терять значимый введённый, но ещё не применённый пользовательский ввод.

В первую очередь это относится к непустому commit message.

Допускается реализовать это через:

- confirmation;
- сохранение draft;
- другой простой и понятный механизм.

Это требование не должно приводить к созданию сложной persistent session model без необходимости.

---

# 44. Не входит в обязательный MVP

На текущем этапе не являются обязательными:

- Clone repository;
- Init repository;
- multi-repository tabs;
- partial/hunk/line staging;
- partial discard;
- полный worktree manager;
- специализированные binary viewers;
- встроенный graphical three-way merge editor;
- полный tag manager;
- Cherry-pick;
- Revert;
- Reset как общий пользовательский workflow;
- управление Git submodules;
- специализированный Git LFS UI;
- sparse-checkout management;
- полноценная поддержка bare repositories;
- собственный credentials manager;
- pixel-perfect reproduction Git Extensions;
- разные UI implementations для Windows/macOS/Linux;
- telemetry;
- localization;
- сложные дополнительные Git workflows, не описанные в этом Intent.

Эти функции могут быть добавлены позже.

Наличие в repository:

- submodules;
- Git LFS;
- других поддерживаемых самим Git extensions

по возможности не должно мешать открыть основной repository или приводить к повреждению его состояния.

# 46. Definition of Done для функций

Функция считается реализованной не только при наличии кода.

Для пользовательского сценария должны выполняться применимые условия:

- проект компилируется;
- automated tests проходят;
- Git operation фактически работает на test repository;
- проверены success и применимые failure scenarios;
- состояние UI обновляется после операции;
- ошибки имеют осмысленное отображение;
- внешний change не оставляет UI надолго в заведомо устаревшем состоянии;
- фактическая Git semantics не заменена собственной упрощённой моделью;
- UI проверен на запущенном приложении через Uno MCP / App MCP, когда такая проверка практически возможна.

Для Git operations, способных остановиться из-за conflicts, DoD также включает проверку соответствующего conflict lifecycle.

# 47. Acceptance criteria первой полноценной версии

Пользователь должен иметь возможность:

1. запустить приложение на Windows или macOS;
2. открыть существующий local Git repository;
3. открыть существующий Git worktree;
4. увидеть commit history и graph;
5. переключить основной scope истории;
6. выбрать commit и просмотреть его metadata;
7. увидеть список изменённых файлов;
8. посмотреть textual unified diff;
9. корректно увидеть обозначение binary file;
10. увидеть working tree changes;
11. отличить staged и unstaged changes одного файла;
12. stage/unstage целый файл;
13. создать commit;
14. при пустом index получить явное предложение stage changes, а не silent staging;
15. amend последний commit;
16. работать с branches;
17. корректно увидеть detached HEAD;
18. видеть local/remote refs и tags;
19. выполнить merge branch;
20. выполнять Fetch, Fetch All, Pull и Push;
21. работать с stash;
22. выполнять необходимые rebase scenarios, включая interactive rebase;
23. увидеть conflicts;
24. разрешать conflicts вручную;
25. выбрать применимую local/current или remote/incoming version;
26. запустить внешний merge tool для одного выбранного файла;
27. запустить общий Start mergetool workflow;
28. stage разрешённый conflict;
29. продолжить либо abort соответствующую Git operation;
30. выполнить Skip там, где Git operation это поддерживает;
31. закрыть и снова открыть приложение во время незавершённого merge/rebase и продолжить работу;
32. discard изменения целого файла с подтверждением;
33. получить обновлённый UI после внешних изменений repository;
34. вручную выполнить Refresh;
35. использовать существующую Git authentication configuration для remote operations;
36. запустить несколько экземпляров приложения с разными repositories.

Приложение должно обеспечивать эти сценарии без необходимости использовать внутреннюю implementation knowledge или вручную исправлять состояние приложения.

# 48. Главный принцип реализации

При выборе между:

- более сложной архитектурой, потенциально полезной когда-нибудь;
- простой реализацией, полностью удовлетворяющей текущему Intent,

следует предпочитать более простое решение.

При этом нельзя упрощать Git semantics.

Не следует заранее строить abstractions для будущих функций, если они не требуются текущим Intent.

Сложность UI и внутренней архитектуры должна появляться только тогда, когда она необходима для уже сформулированного пользовательского поведения.

Если Intent не определяет конкретную деталь пользовательского Git workflow, сначала следует посмотреть на соответствующее поведение Git Extensions, а не изобретать новую продуктовую semantics без необходимости.
