# IDD-0046 — Git submodules

## Intent

CSharpGit supports Git submodules as references to commits of distinct Git
repositories. The parent repository owns the gitlink reference; each initialized
submodule repository owns its own files, index, commits and branches. Users can
inspect, initialize, safely update and open submodules through existing workflows
without a separate nested repository-management system.

## Behavior

- Tracked gitlinks are recognized even when clean or not initialized. They appear
  as distinct entries in the existing file tree, and users can inspect their
  relative path, configured URL when available, recorded commit, current checkout
  commit and branch when available, and local modifications.
- Initialization, checked-out commit mismatch, modified tracked contents,
  untracked contents and conflicts/errors remain distinguishable and may overlap.
  A normal detached HEAD checkout is not considered a failure.
- Historical snapshots represent the commit recorded at that point in the parent
  history, not the submodule's current local checkout. Commit-reference changes
  are shown as old/new Git commit identifiers rather than ordinary file diff.
  Browsing historical information does not fetch submodule history.
- An initialized submodule can be opened independently using CSharpGit's
  repository-opening workflow, preferably in another process without replacing
  the parent workspace. A non-initialized submodule offers initialization instead.
- Initialize retrieves the commit recorded in the parent; Update to Recorded
  Commit returns the submodule to the parent index's gitlink commit.
  Neither update action means advancing to the newest remote branch commit.
  Update All Submodules also initializes nested submodules recursively.
- Long-running operations are cancellable, show progress and preserve Git's
  original failure information. Local modifications that could be overwritten
  prevent unsafe updates. No forced checkout, reset or cleanup is performed.
- Parent Working Tree shows gitlink revisions separately from dirty internal
  submodule files. Stage and Unstage change only the parent index's commit
  reference; internal files require opening and committing the submodule itself.
  Stage on a dirty submodule with no changed commit must not pretend that its
  internal changes were staged.
- Discard Selected, Discard All, folder and staged Discard cannot remove or reset
  local submodule changes. Unsupported discard actions are disabled or excluded
  from group operations without hiding the safety restriction.
- Clone offers an optional Initialize submodules choice. It is off by default;
  when enabled, Git recursively initializes submodules and the operation only
  succeeds after the requested recursive initialization succeeds.
- Explicit and reactive refresh reflect external Git operations while keeping
  selection and unrelated UI state stable.

## Durable Architecture And Constraints

- Git remains the source of truth; no independent authoritative submodule state
  database or second Git implementation is introduced.
- Local gitlink records and local checkout state are distinct from historical
  commit snapshot data.
- Parent actions must not stage, discard, commit or clean internal submodule
  files. Submodule editing is delegated to the existing repository UI.
- Paths, arguments, cancellation and error reporting follow the existing
  secure Git execution boundary. Git authentication, transport permissions and
  protocol policy are not bypassed by application code.
- A damaged or inaccessible submodule must not crash the host application or
  corrupt neighboring submodules.

## Non-Goals

Creating or deleting gitlinks through the GUI, editing submodule URLs, tracking
remote branch tips, simultaneous multi-submodule branch management, implicit
submodule commits, custom fetch/authentication, an embedded submodule manager,
Gitlink conflict resolution UI and recursive browsing of nested history.

## Acceptance Criteria

- A parent project displays clean, dirty, conflicting and uninitialized gitlinks
  with true Git-derived status and distinct visual treatment.
- Users can inspect their recorded and checked-out commits, initialize, safely
  update and open initialized submodules.
- Changing a checked-out submodule commit can be staged, unstaged and committed in
  the parent without also staging or destroying internal changes.
- Normal parent discard workflows never destroy submodule-local data.
- Clone supports both ordinary non-recursive behavior and opt-in recursive
  initialization, preserving Git failures on errors.
- No new always-visible panel, duplicate Git backend or non-Git authoritative
  model is required.

## Verification

- Automated local temporary Git repositories exercise clean/uninitialized
  discovery, initialization, commit mismatch, internal dirty/untracked content,
  stage/unstage/commit, safe discard, update, failure paths and recursive nesting.
- Tests verify URL/path handling including whitespace and Unicode; local-only
  remotes do not require network services or modify production protocol policy.
- Refresh is checked after mutations by external Git tools. Snapshot inspection
  distinguishes historical gitlinks from the live checkout.
- Regression tests cover ordinary staging, discard, commits, refresh and cloning
  in repositories without submodules.
- Platform checks are run on Windows and macOS when CI execution is available.
