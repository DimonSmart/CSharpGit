# IDD-0006.spec-refs-and-remotes

## Intent

Пользователь видит и управляет основными Git refs и выполняет стандартные remote
operations через существующую конфигурацию и authentication инфраструктуру Git.

## Behavior

- UI отображает local branches, remote branches, настроенные remotes и tags;
  текущая branch и refs на commits видны однозначно.
- Для current branch с configured upstream compact toolbar показывает ненулевое
  расхождение прямо на соответствующих действиях: `Pull ↓N` для behind и
  `Push ↑N` для ahead. Нулевое значение и отсутствие upstream не добавляют
  счетчик; при divergence одновременно видны оба счетчика.
- Default branch определяется по primary remote, обычно `origin`, через remote HEAD,
  а не по именам `main`, `master` или другим соглашениям. Валидный локальный
  `<remote>/HEAD` используется в первую очередь; при его отсутствии или
  некорректности допускается запрос `ls-remote --symref <remote> HEAD`.
- Remote default branch получает признак default. Local branch получает этот
  признак только если ее configured upstream точно указывает на remote default
  branch; совпадение имен само по себе ничего не означает.
- Если primary remote или его default branch определить нельзя, приложение не
  угадывает значение и не помечает ни одну branch как default.
- Fetch обновляет локальную информацию remote HEAD, поэтому смена default branch
  на remote отражается после последующего refresh repository state.
- Доступны checkout/switch, создание branch и удаление branch, когда Git это
  позволяет.
- Detached HEAD распознается и не отображается как обычная current branch.
  Действия, требующие branch, следуют Git semantics либо недоступны с понятным
  объяснением.
- При checkout remote branch поддерживается нормальный сценарий создания local
  tracking branch, когда он необходим.
- Pull по умолчанию использует configured upstream текущей branch.
- Push использует стандартную Git configuration. Если необходимый upstream
  отсутствует, пользователь явно выбирает remote/branch и при необходимости
  устанавливает upstream; приложение не выбирает произвольную remote branch.
- Поддерживаются Fetch, Fetch All, Pull и Push; после завершения UI обновляет
  соответствующее состояние репозитория.
- Remote operations используют стандартные authentication mechanisms пользователя,
  включая применимые credential helpers, Git Credential Manager, SSH
  configuration и SSH agent.
- Authentication failures отображаются как понятные Git errors.
- Tags поддерживают normal everyday lifecycle: просмотр lightweight и annotated
  metadata, создание на HEAD или выбранном historical commit, local deletion,
  push одного tag, push всех tags, fetch tags, remote deletion, detached checkout,
  branch creation from tag и reference-scoped history.
- Annotated tag хранит собственные tagger/date/message и tag object id. Его target
  для history/navigation всегда peeled commit; lightweight tag не получает
  выдуманную дату создания или metadata commit-а.
- Обычный Push Tag никогда не перемещает существующий remote tag. Совпадающий tag
  считается up to date, несовпадающий требует отдельного явного force-update flow
  с подтверждением старого и нового target.
- Remote tag state не моделируется persistent tracking refs приложения. Наличие и
  target remote tag запрашиваются у Git/remote по требованию.
- По умолчанию tags сортируются Git semantics `-version:refname`; explicit effective
  `tag.sort` пользователя имеет приоритет, а `versionsort.suffix` сохраняет обычный
  Git смысл.

## Durable Architecture And Constraints

- Приложение не хранит собственные passwords, access tokens или SSH private keys.
- Git configuration является основным контрактом для upstream, push behavior,
  tag ordering и authentication.
- Default-branch metadata является производным состоянием Git refs/upstream и не
  хранится как независимая пользовательская настройка.
- Tag state и remote-tag state выводятся из Git; отдельной persistent tag database
  или application-specific tag sort setting нет.
- Tag metadata читается bounded Git operation, а не отдельным Git process на каждый
  tag; repositories с большим количеством tags не должны создавать N-process
  refresh behavior.
- Presentation использует semantic reference/tag operations и не строит raw Git
  commands из пользовательских tag names.
- Remote operations выполняются без блокировки UI.

## Non-Goals

- Полноценный собственный credentials manager.
- Сложный отдельный remote-management subsystem без необходимости для основных
  операций.
- Создание signed tags, signature verification UI и изменение существующего
  annotated tag message.
- GitHub/GitLab releases, release notes generation и отдельный permanent tag manager.
- Tagging arbitrary blobs/trees как UI workflow.

## Acceptance Criteria

- Пользователь различает local и remote branches, видит current branch, remotes,
  tags и detached HEAD.
- Для tracked current branch toolbar показывает `Pull ↓N` только при `Behind > 0`
  и `Push ↑N` только при `Ahead > 0`; при divergence отображаются оба значения,
  а при нулевых счетчиках или отсутствии upstream подписи остаются обычными.
- `origin/HEAD -> origin/main` определяет `origin/main` как remote default branch.
- Local `main` помечается default только при upstream `origin/main`; local branch
  с тем же именем и другим upstream не помечается.
- Имена default branch не ограничены `main` и `master`.
- После обновления remote information смена remote HEAD отражается в repository
  state; при неизвестном default branch маркер отсутствует.
- Пользователь выполняет основные branch operations и нормальный checkout remote
  branch.
- Fetch, Fetch All, Pull и Push используют существующую Git configuration и
  обновляют UI.
- Отсутствующий upstream требует явного выбора, а не скрытого решения приложения.
- Существующая authentication configuration работает без переноса секретов в
  собственное хранилище приложения.
- Пользователь может без terminal создать lightweight/annotated tag на HEAD или
  historical commit, увидеть его metadata и commit badge, push/fetch его, создать
  branch или detached checkout, открыть history и удалить tag локально/удаленно.
- Destructive local delete, remote delete и force-update remote tag требуют явного
  modal confirmation; cancel является безопасным default.
- Version-like tags (`v1.9`, `v1.10`, `v1.11`) отображаются в Git version order, а
  explicit `tag.sort` и `versionsort.suffix` пользователя соблюдаются.
- Normal tag push не force-updates опубликованный tag и не влияет на branch push.

## Verification

- Проверяются local/remote refs, tags, detached HEAD и branch operations на
  реальном тестовом репозитории.
- UI contract проверяет подписи Pull/Push для ahead-only, behind-only, divergence,
  synchronized branch, отсутствующего upstream и detached HEAD.
- Проверяются default remote HEAD, local upstream matching, несовпадающий upstream,
  нестандартное имя default branch, смена remote default branch и отсутствие
  информации о default branch.
- Проверяются configured upstream, отсутствующий upstream и установка upstream по
  явному выбору.
- Проверяются успешные и неуспешные remote operations, authentication failures,
  неблокирующий UI и последующее обновление refs.
- На реальных temporary repositories проверяются lightweight/annotated metadata и
  peeling, Unicode и slash names, Git version sorting/config overrides,
  create/delete invariants и отсутствие изменений index/working tree.
- С temporary bare remote проверяются push one/all, up-to-date, conflicting remote
  tag, confirmed force update, remote deletion preserving local tag, fetch и fetch
  collision without silent force.
- UI contract tests проверяют contextual menus, safe confirmation defaults,
  mutation/busy gating, navigation-only tag selection и отсутствие Presentation
  re-sorting после порядка, установленного tag/ref layer.
