# IDD-0018 — Manual refresh and external repository change indicator

Status: Current

## Intent

CSharpGit keeps an opened repository as a stable UI snapshot until refresh is explicitly owned by the application. External filesystem or Git changes must be visible as a refresh-required signal, not as an automatic repository reload.

A full repository refresh is performed only when:

- the repository is opened initially;
- the user explicitly invokes the existing Refresh action;
- a Git operation initiated by CSharpGit completes and its result must be reflected immediately.

Window focus, activation and deactivation are not repository changes and never trigger refresh.

## External repository change monitoring

`RepositoryChangeMonitor` observes both the opened repository working directory and the repository's actual `GitDirectory`. The latter is used instead of assuming `.git`, so linked worktrees remain supported.

Working-tree file creation, deletion, rename, content/size/timestamp changes and directory changes mark the repository as externally changed. A file must be able to trigger the signal repeatedly even when its Git status was already `Modified` before the latest edit.

Git metadata changes are also observed recursively, including HEAD, index, refs, stash refs and merge/rebase/cherry-pick/revert state files and directories.

Filesystem notifications are debounced/coalesced before the monitor raises `RepositoryChanged`. The monitor only reports change; it never reads repository state, history, refs or diffs and never invokes a refresh operation.

## Refresh-required state and UI

An external `RepositoryChanged` notification sets `IsRefreshRequired = true` on the active repository presentation.

The top-toolbar Refresh action is a single compact icon-only button and is also the refresh-state indicator. There is no separate toolbar busy ring beside it.

The button has three visual states:

- **Up to date** — the circular Refresh icon is static and green.
- **Refresh required** — the same static icon is red. Its tooltip is `Repository has changed externally. Refresh to see the latest state.`
- **Refreshing** — the static icon is replaced by a spinning yellow progress ring for the duration of the user-invoked full Refresh action. Its tooltip is `Refreshing repository…`.

The normal tooltip is `Refresh repository.` The Refresh button remains the user action in every non-running state. Repeated clicks while that Refresh action is already running do not start another refresh.

The yellow state is specific to the explicit repository Refresh action; generic `IsBusy` from Fetch, Push, Commit or another Git operation must not turn the Refresh button yellow merely because the application is busy. Those operations keep their existing operation/status feedback.

A successful repository state refresh acknowledges the monitor baseline and clears `IsRefreshRequired`. This applies to an explicit user refresh and to the post-operation refresh after a CSharpGit-initiated Git mutation.

## Internal operations and acknowledgement

Existing internal Git-operation refresh semantics remain unchanged: working-tree-only mutations may use the state-only refresh defined by IDD-0014, while history-changing operations refresh history as required.

Filesystem events caused by an internal operation must not leave the external-change indicator set after the operation's post-refresh state has been read successfully. Monitor acknowledgement creates a new watcher generation and cancels/deprecates pending notifications from the previous generation. A genuinely new change that occurs after acknowledgement must still be reported.

Reopening the repository is never used as a refresh mechanism.

## UI stability

Receiving an external-change notification does not:

- rebuild the repository tree;
- read or replace commit history;
- read or replace working-tree state or refs;
- change the selected commit or working-tree selection;
- reset scroll position;
- reload a diff;
- animate the Refresh indicator;
- cause workspace flicker.

Until Refresh is invoked, the user continues to see the previously loaded repository snapshot.

## Compatibility with IDD-0014

IDD-0014 refresh-stability invariants remain normative. In particular, an opened `Repository` identity is retained, ordinary refresh never calls `IRepositoryService.OpenAsync`, state-only mutations do not reread history, collection updates remain bulk/coalesced, durable selection anchors remain intact, and repository-tree expansion/session state is preserved.

## Verification

Verify the following scenarios:

1. Open a repository and leave it idle for several minutes: the workspace does not rebuild or flicker and the Refresh icon remains static green.
2. Switch focus repeatedly between CSharpGit and other applications: no repository refresh occurs.
3. Modify a tracked file in an external editor: the Refresh icon becomes red while the rest of the UI remains unchanged.
4. Modify an already-modified file again: Refresh remains or becomes required again.
5. Commit from a terminal: the Refresh icon becomes red and displayed history remains unchanged until Refresh is invoked.
6. Checkout, rebase or fetch from a terminal: the red indicator appears without automatic UI reconstruction.
7. Invoke Refresh: the button shows the spinning yellow ring while the explicit refresh is running; working tree, refs and history update; after completion the indicator returns to static green.
8. Stage, Commit, Checkout and Fetch through CSharpGit: existing immediate UI updates still occur, generic busy state does not by itself show the yellow Refresh ring, and the external-change indicator is clear after the post-operation refresh.
9. The toolbar contains only the combined Refresh button/indicator; the former adjacent `BusyIndicator` is absent.
10. Existing IDD-0014 regression and integration coverage continues to pass.

Automated coverage should include working-tree notifications, Git-metadata notifications, debounce/coalescing, repeated notification after acknowledgement, dropping stale pre-acknowledgement events, activation not calling refresh, the green/red/yellow indicator contract, absence of the separate toolbar busy indicator, explicit-refresh-only animation and monitor lifecycle cleanup.
