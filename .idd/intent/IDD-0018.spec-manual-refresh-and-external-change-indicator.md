# IDD-0018 — Manual refresh and semantic external repository change indicator

Status: Current

## Intent

CSharpGit keeps an opened repository as a stable UI snapshot until refresh is explicitly owned by the application.

Filesystem activity is not itself a repository change. `FileSystemWatcher` is an invalidation mechanism only. Refresh Required means that Git-visible state affecting the displayed repository snapshot differs from the last state successfully loaded by CSharpGit.

A full repository refresh is performed only when:

- the repository is opened initially;
- the user explicitly invokes Refresh;
- a Git operation initiated by CSharpGit completes and its result must be reflected immediately.

Window focus, activation and deactivation never trigger refresh.

## Invalidation monitoring

`RepositoryChangeMonitor` observes:

- the working directory;
- the worktree-specific `GitDirectory`;
- `GitCommonDirectory` for linked worktrees.

Metadata roots are deduplicated when one recursively contains another.

Filesystem notifications are trailing-edge debounced/coalesced. `RepositoryChanged` means only `repository may have changed`.

The monitor does not read Git state, history, refs or diffs and does not change UI state. It does not decide whether an event is Git-visible.

Obvious metadata lock noise such as `*.lock` and `index.lock` is ignored before probing. Other metadata activity remains coarse invalidation.

Acknowledgement must not recreate watchers or unconditionally discard pending pre-acknowledgement events. Invalidation generation is monotonic so a change occurring during refresh/probe is not lost.

## Semantic probe and displayed baseline

After coalesced invalidation CSharpGit performs a local, read-only Git probe and compares the result with the displayed baseline.

The baseline represents the snapshot loaded into the UI, not the latest state observed by the monitor.

The probe covers at least:

- HEAD/ref and detached state;
- staged/index state;
- unstaged tracked content;
- untracked non-ignored paths and content;
- local branches;
- remote-tracking branches;
- tags;
- stash entries;
- remote configuration that is displayed;
- repository-local merge-tool configuration that is displayed;
- merge/rebase/cherry-pick/revert/bisect state.

Repeated edits are significant even when XY status does not change. Therefore the probe includes semantic index object IDs and content fingerprints for Git-visible changed/untracked working-tree files.

Ignored files do not participate in the fingerprint. Git defines ignore semantics; CSharpGit does not implement a `.gitignore` parser.

Filesystem timestamps and raw `.git/index` bytes are not semantic equality.

## Local-only background behavior

Every Git command used specifically by the background probe runs with optional locks disabled:

`GIT_OPTIONAL_LOCKS=0`

The probe never performs network operations such as `fetch`, `ls-remote` or remote default-branch discovery.

Background probing never:

- opens/reopens the repository;
- loads commit history;
- loads a diff into the UI;
- modifies observable collections;
- changes selection;
- performs a full Refresh.

Probe failures keep the current indicator state, are diagnostic-only and do not stop future monitoring.

## Single-flight/coalescing

Background probes never run in parallel.

If filesystem invalidation arrives while a probe is running, CSharpGit marks one pending probe. When the current probe finishes, at most one additional probe runs for all invalidations accumulated in the meantime.

There is no periodic Git polling.

`RepositoryStateSession` remains an explicit state holder with `Current`, `RefreshAsync`, `RunMutationAsync` and `StateChanged`, but it does not own a timer.

## Refresh Required and UI

A watcher notification does not directly set `IsRefreshRequired`.

```text
filesystem activity
        ↓
coalesced invalidation
        ↓
local Git probe
        ↓
compare with displayed baseline
        ↓
same      -> keep Refresh green
different -> Refresh red
```

External invalidation does not automatically rebuild any UI.

The Refresh toolbar button keeps three states:

- **Up to date** — static green Refresh icon.
- **Refresh required** — static red Refresh icon, tooltip `Repository has changed externally. Refresh to see the latest state.`
- **Refreshing** — yellow progress ring only for the explicit Refresh action, tooltip `Refreshing repository…`.

A successful refresh publishes a new displayed baseline. A post-refresh probe verifies current state against it. Delayed watcher events from CSharpGit's own mutation therefore stay green when current state still equals the displayed baseline, while a real change racing with refresh remains detectable.

## Internal operations

Stage, Unstage, Commit, Checkout, Fetch, Pull, Push, Reset, Rebase, Cherry-pick, Revert, Stash and other CSharpGit mutations keep their existing post-operation refresh behavior.

Events caused by CSharpGit's own operation do not require file allowlists. After the displayed baseline is updated, delayed events are handled through the same semantic probe.

## RepositoryState equality

Semantic equality of `RepositoryState` is implemented once in reusable application logic.

`ReadAtUtc` is excluded.

Collections whose order is not semantically meaningful are compared order-independently.

## Linked worktrees

`Repository` exposes both `GitDirectory` and `GitCommonDirectory`.

For a normal repository they are equal. For a linked worktree they may differ. Shared refs, packed refs, remote-tracking refs, tags, stash and configuration under the common directory therefore remain observable.

## Verification

Automated coverage includes:

1. repeated edit of an already-modified tracked file changes the fingerprint;
2. repeated edit of an existing untracked non-ignored file changes the fingerprint;
3. ignored build/IDE/indexing activity leaves the fingerprint unchanged;
4. repeated external staging with unchanged XY status changes the fingerprint;
5. probe does not rewrite `.git/index`;
6. probe remains local-only even when an unreachable remote is configured;
7. metadata lock files do not publish invalidation;
8. acknowledgement does not drop a queued invalidation;
9. linked-worktree shared `GitCommonDirectory` changes are observed;
10. `RepositoryStateSession` does not poll on a timer;
11. semantic repository-state collections compare independently of irrelevant ordering.

The user-visible acceptance criterion is that `dotnet build`, `dotnet test`, Visual Studio background activity and LocalVectorSearchMcp indexing can continuously modify ignored files while Refresh remains green, but Git-visible state that makes the displayed snapshot stale turns Refresh red without automatically refreshing the UI.
