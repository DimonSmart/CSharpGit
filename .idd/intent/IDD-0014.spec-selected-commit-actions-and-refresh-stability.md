# IDD-0014 — Selected commit actions and refresh stability

Status: Current

## Intent

CSharpGit must provide the common actions for a selected history commit without requiring the CLI, while repository-state mutations must not make the workspace appear to reopen.

The history context menu acts on the row under the pointer and uses the full commit hash. It contains:

- Copy hash
- Create branch here…
- Create tag here…
- Checkout this commit
- Delete tag → local tags on the selected commit
- Cherry-pick
- Revert
- Reset current branch to here → Soft / Mixed / Hard

The menu is available both in all-references history and when viewing a specific reference.

## Commit actions

Copy hash is presentation-only: it copies the full hash and performs no Git command or refresh.

Create branch delegates to `IReferenceService.CreateBranchAsync` with the selected commit as the start point. The dialog asks for the branch name and whether to switch to it. Invalid names and existing branches are reported as Git/application errors.

Checkout selected commit delegates to `CheckoutAsync` and enters detached HEAD after an explicit confirmation. Local changes are governed by Git; CSharpGit does not stash or discard them automatically.

Delete tag is a dynamic submenu built from the current local tag state. It matches `GitTag.TargetCommit` to the selected commit's full hash with ordinal comparison, preserves the existing tag order, remains visible but disabled when no local tag is present or tag mutations are unavailable, and routes deletion through the same safe local-tag confirmation and `ITagService.DeleteTagAsync` workflow used by Repository Tree. Remote tags are not deleted.

Cherry-pick and Revert are real Git operations. They expose Completed, Conflicts and Failed results and integrate with the existing `RepositoryOperation.CherryPick` / `RepositoryOperation.Revert` Continue / Abort / Skip lifecycle. A merge commit always requires the user to explicitly choose the 1-based mainline parent. Revert uses `--no-edit`.

Reset delegates directly to `git reset --soft|--mixed|--hard`. It is available only while HEAD is attached to a local branch and no other Git operation is in progress. Hard reset requires a destructive confirmation that states tracked uncommitted changes are lost and untracked files are not deleted.

After a successful create-and-switch, checkout or reset, selection remains on the target commit. Successful cherry-pick/revert selects the new HEAD where that commit is visible.

## Refresh invariants

Opening a repository creates its `Repository` identity. Refreshing an already-open repository must never call `IRepositoryService.OpenAsync` and must never replace that `Repository` object.

State-only refresh is used for Stage, Stage selected/all, Unstage, Unstage selected/all and Discard. These operations do not reread commit history. History-changing actions use state + history refresh.

A repository-state snapshot is applied to observable presentation state as a logical transaction. Source ViewModel collections may still use bulk `Reset`, but their notifications are coalesced into at most one Repository Tree reconciliation for that snapshot. Existing logical Repository Tree nodes keep reference identity across ordinary refresh cycles, and tree collections express changes with `Add` / `Remove` / `Move` rather than `Reset`.

Stage/Unstage does not clear active working-tree selection before Git runs. The repository-relative path is the durable selection anchor, so an active file can move between Unstaged and Staged while remaining active. Stale asynchronous diff work remains cancellation/generation protected.

Cancel from the empty-index commit choice only closes that choice. It performs no Git command, no refresh, no history read, and preserves the commit message and working-tree presentation.

Repository tree expansion/session state and surviving selection must not be reset by ordinary refresh. Ordinary refresh reconciles a stable presentation tree instead of rebuilding it; a different repository may start a new repository-specific navigation session. Reopening the same repository as a refresh mechanism is forbidden.

## Verification

Integration coverage uses real temporary Git repositories for historical branch creation, detached checkout, cherry-pick, revert, merge-mainline behavior and soft/mixed/hard reset semantics. Conflict tests verify the existing operation lifecycle. Hard-reset coverage verifies untracked files survive.

Regression/contract coverage verifies that refresh no longer reopens a repository, working-tree mutations use state-only refresh, repository-state collection application is bulk/coalesced into one tree reconciliation, unchanged tree nodes retain identity without collection `Reset`, selection is not cleared before stage/unstage, Cancel Commit remains side-effect free, and the commit context menu exposes the required actions.

All existing tests must continue to pass. Desktop/manual verification should exercise repeated Stage/Unstage, multi-selection staging, empty-index Commit → Cancel, and all selected-commit actions without workspace/tree/history flicker.
