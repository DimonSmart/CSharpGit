# IDD-0042.adr-repository-sync-presentation-boundary

## Status

Accepted

## Context

Repository synchronization was split across three Presentation owners. `OpenRepositoryViewModel`
held remotes, selected remote and basic Fetch/Pull/Push commands; `MainPage` directly used
`IRepositorySyncService` for push and force-push workflows; and `BranchesViewModel` owned
publish-current-branch operations. This duplicated lifecycle decisions, allowed some remote
mutations to bypass the repository mutation gate, and made the View classify application-level
Git exceptions.

The existing repository-switching contract requires asynchronous work to remain bound to the
repository for which it was started. The safe-force-push contract additionally requires the exact
immutable `ForcePushWithLeaseSnapshot` shown in the confirmation dialog to be the snapshot
passed to execution.

## Decision

Introduce `RepositorySyncViewModel` as the Presentation owner for repository synchronization
and publication.

`RepositorySyncViewModel` owns:

- configured remotes and selected-remote presentation state;
- Fetch, Fetch All and Pull;
- ordinary Push and `AutoSetupRemoteOnPush` policy;
- explicit Push To / Publish Branch preparation and execution;
- force-push-with-lease preparation, application-exception classification and execution;
- sync-operation availability and repository-identity checks.

It depends directly on `IRepositorySyncService` and `IAppSettingsService`. It does not depend
on `MainPage`, `SettingsWindowController`, other sibling ViewModels, dialogs, windows or a
service locator.

`OpenRepositoryViewModel` composes the feature and implements the narrow
`IRepositorySyncContext`. The context exposes only the current repository, shared busy/current
operation state, canonical current local branch, and the existing serialized mutation/refresh
lifecycle. Canonical remotes live only in `RepositorySyncViewModel`; branch, tag and history
contexts read that collection through the parent adapter.

`MainPage` remains the owner of user interaction: target selection, confirmations and result
dialogs. It calls semantic `RepositorySyncViewModel` operations and receives explicit result
types. It must not inject `IRepositorySyncService`, classify sync application exceptions, or
perform a second backend refresh after a sync mutation.

`BranchesViewModel` continues to own branch lifecycle, including remote branch deletion.
Therefore it may still depend on `IRepositorySyncService` for `DeleteRemoteBranchAsync`, but
publish-current-branch and push-destination workflows belong to `RepositorySyncViewModel`.

Force-push-with-lease keeps the existing safety invariant: preparation returns an immutable
`ForcePushWithLeaseSnapshot`; the View may display it, but execution receives that exact object
without re-preparing remote state.

The backend `IRepositorySyncService` contract and Git semantics are unchanged by this decision.

## Alternatives Considered

Keep synchronization in `OpenRepositoryViewModel`. Rejected because the parent would continue
to own feature-specific state and backend dependencies after the rest of Presentation had been
decomposed.

Keep push orchestration in `MainPage`. Rejected because a View would continue to classify
application exceptions, perform backend calls and bypass the common mutation lifecycle.

Move all uses of `IRepositorySyncService` into the sync feature. Rejected because remote branch
deletion is a branch-lifecycle user intent and belongs in `BranchesViewModel` even though its
backend method is exposed by the synchronization service.

Make `RepositorySyncViewModel` depend on `BranchesViewModel`. Rejected because sibling
ViewModel dependencies obscure ownership. The parent context exposes only the canonical current
local branch needed by synchronization.

## Consequences

Remote mutations use one repository-aware serialization and refresh path. Repository switches
cannot cause a prepared operation for repository A to execute against repository B.

The View is limited to choosing which dialog to show from structured results. Application sync
exceptions stop at the feature boundary.

Remotes have one authoritative Presentation collection. Consumers must use
`OpenRepositoryViewModel.RepositorySync.Remotes` or a narrow context projection; forwarding
properties on the parent are intentionally not provided.

Branch deletion remains independently evolvable from repository synchronization, while publish
and force-push behavior can evolve inside the sync feature without increasing MainPage backend
knowledge.

## Supersedes

None.
