# IDD-0007.spec-git-workflows

## Intent

Приложение предоставляет понятные desktop workflows для stash, merge и rebase,
делегируя изменение репозитория Git и сохраняя его semantics во всех исходах.

## Behavior

- Основная кнопка `Pull` запускает одно нативное `git pull --prune` с сохранённой
  глобальной стратегией; вариант выполнения выбирается приложением только через
  аргументы конкретной команды: `Git configuration` (без reconcile override),
  `Merge` (`--no-rebase`), `Rebase` (`--rebase`),
  `Fast-forward only` (`--ff-only`). Для каждого режима доступен
  одноразовый запуск без изменения preference.
- Компактное меню `Pull` позволяет изменить default strategy отдельно от
  запуска Git, сохраняя основной однокликовый Pull и current-branch `Pull ↓N`.
  Tooltip сообщает upstream и выбранную политику.
- `Force Git autostash` при включении добавляет `--autostash`;
  выключение не добавляет `--no-autostash`, оставляя работу действующему
  Git config. Приложение не использует ручные stash push/pop для Pull.
- Результат Pull разделяет `Completed`, `NeedsAttention`, `Refused`, `Failed`
  и необязательную классификацию способа успешной интеграции. Останавливающиеся
  merge/rebase и index conflicts после autostash определяются реальным Git state,
  а не сообщением Git или одним exit code. После Pull применяется единый
  repository mutation/refresh workflow, в том числе при отказе и отмене.


- Repository-level `Stash…` доступен из корневой группы `Stashes` и Commit area;
  оба entry point запускают один dialog/application workflow.
- Repository-level stash поддерживает `All tracked changes`, `Staged changes only`
  и отдельный `Include untracked files` для ordinary stash. Ignored files и `--all`
  не включаются. Staged-only использует настоящий `git stash push --staged`.
- Working Tree file leaves поддерживают selected-path stash для одного или нескольких
  explicit files. Выбор из Staged tree не означает `--staged`; path сохраняется целиком.
  Selected untracked paths автоматически включают `--include-untracked`.
- Selected-path stash учитывает обе стороны rename, literal pathspec semantics и
  NUL-separated `--pathspec-from-file` для больших selection. Один request запускает
  один `git stash push`, а temporary resource очищается при success/error/cancellation.
- Создание stash делегируется Git; после любого завершившегося mutation attempt,
  включая failure после частично выполненного `--staged`, приложение перечитывает
  authoritative repository state и не выполняет собственный rollback.
- Stash отображается как отдельный repository object. Viewer восстанавливает стандартную
  Git структуру `H` (base), `I` (saved index), `W` (stash commit) и optional `U`
  (saved untracked tree), а Changes является union файлов `H→W`, `H→I`, `I→W`
  и `U`.
- Tracked change metadata показывает historical `staged`, `unstaged` или
  `staged + unstaged`; untracked files имеют отдельный state. Primary tracked diff
  остаётся combined `H→W`; net-zero file не исчезает и получает explicit informational
  state вместо пустого безымянного diff.
- Stash-specific actions: Apply, Pop и destructive Drop. Apply использует stable stash
  commit hash; Pop/Drop непосредственно перед mutation проверяют, что positional
  `stash@{N}` всё ещё resolves в выбранный stable commit. `--index` автоматически
  не используется.
- Пользователь может merge выбранную branch в current branch.
- Merge сохраняет применимые исходы Git: fast-forward, merge commit, отказ Git и
  conflicts. Приложение не эмулирует merge самостоятельно.
- После успешного merge обновляются history, graph, refs, working tree и index.
- Пользовательский Interactive Rebase показывает настоящий текстовый
  `git-rebase-todo`. CSharpGit строит только исходный linear-range todo, затем
  добавляет blank line и встроенный comment help с short/long формами основных
  команд. После ручного редактирования именно Git интерпретирует commands, порядок,
  comments, blank lines и допустимый синтаксис установленной версии Git.
- Raw todo открывается в одном специализированном text editor surface с
  line-number gutter, `NoWrap`, вертикальной и горизонтальной прокруткой и
  визуально приглушёнными comment lines. Help является обычной частью raw todo:
  его можно редактировать, переставлять или удалить, и Presentation не удаляет
  comments перед запуском Git.
- Raw editor может иметь узкие UX helpers, которые только подготавливают стандартный
  Git syntax в видимом todo. `Change author…` использует textual selection/caret
  существующего editor, распознаёт только необходимые commit commands и собственные
  marker blocks CSharpGit и не превращает todo в отдельный visual plan, parser или DSL.
- `Change author…` применяется только к самостоятельным `pick/p`, `reword/r`
  и `edit/e`. `squash/s`, `fixup/f` и базовый commit соответствующей
  squash/fixup group исключаются: author меняется только там, где generated
  `exec` однозначно относится к итоговому standalone commit.
- Helper вставляет непосредственно после commit обычный comment-marked block с
  `exec git commit --amend --no-edit --no-verify --no-gpg-sign ...`. Explicit mode
  использует `--author 'Name <email>'`; reset mode использует стандартный Git
  `--reset-author` и не материализует name/email в raw todo.
- По умолчанию existing AuthorDate сохраняется. Для explicit mode это означает
  отсутствие `--date`; для reset mode generated command сохраняет текущую author
  date переписываемого `HEAD` через
  `--date="$(git show -s --format=%aI HEAD)"`. Опция `Reset author date as well`
  добавляет `--date=now` в explicit mode, а в reset mode оставляет один
  `--reset-author`, который штатно обновляет author timestamp.
- Reset-to-current-identity разрешается Git непосредственно при выполнении generated
  `exec`, поэтому учитывает обычную Git identity semantics на момент запуска rebase.
  Effective `user.name`/`user.email`, если доступны через Repository Git Identity
  (IDD-0041), показываются в helper только как informational hint и не являются
  источником значения для generated reset command.
- `Change author…` следует compact design system (IDD-0019): использует shared
  typography/control/spacing resources, не держит explicit Name/Email controls
  видимыми в reset mode и сохраняет action buttons доступными в компактном flyout
  с vertical-scroll fallback для ограниченной высоты окна.
- Apply у `Change author…` меняет только raw todo text. Repository, refs, commits и
  working tree остаются неизменными до существующего `Start rebase`, который
  по-прежнему запускает обычный raw `StartInteractiveRebaseTodoAsync`.
- Пользовательский Interactive Rebase имеет один contextual entry point:
  `Interactive rebase from here…` в context menu History. Он открывает общий raw
  todo workflow, dedicated text editor и настоящий `git rebase --interactive`
  execution path; global/manual `onto` input отсутствует.
- History entry point трактует выбранный полный commit SHA как `onto` для
  настоящего `git rebase --interactive <selected>`. Выбранный commit остаётся
  неизменной базой и не попадает в todo; первой строкой становится следующий commit
  по пути к текущему HEAD. Shortcut доступен только при attached local HEAD, но
  окончательная ancestry/topology/state validation выполняется после клика.
- Текущий пользовательский Interactive Rebase поддерживает только linear source
  ranges. Если `base/upstream..HEAD` содержит merge commit, editor не открывается.
  Raw editor сам по себе не включает `--rebase-merges`.
- Raw todo не преобразуется обратно в `InteractiveRebasePlan`, не проверяется
  через `RebaseAction` allowlist и не нормализуется перед передачей Git.
- Managed `InteractiveRebasePlan` остаётся внутренним mechanism для workflows,
  которым нужна детерминированная rewrite semantics, прежде всего
  `Edit commit message…`.
- Merge или rebase, остановившиеся из-за conflicts, переходят в общий conflict
  workflow и оставляют repository в реальном состоянии незавершенной operation.
- Raw rebase может штатно остановиться без conflict из-за `edit`, `break`,
  failed `exec`, editor failure или другой sequencer pause. Такое состояние
  представляется как `RebaseResultKind.Paused`, если repository всё ещё находится
  в `RepositoryOperation.Rebase`.

## Durable Architecture And Constraints

- Mutating workflows выполняются самим Git или совместимым с Git механизмом, а не
  собственной эмуляцией приложения.
- Каждый завершившийся или остановившийся workflow приводит к перечитыванию
  фактического состояния repository.
- Подготовленный raw Interactive Rebase todo хранит source snapshot: полный HEAD
  SHA и canonical symbolic HEAD ref. Перед реальным `git rebase --interactive`
  service повторно проверяет operation, HEAD/ref identity, существование выбранного
  base commit и linear topology. Пользователь не редактирует `onto` вручную.
- Narrow scanning для textual selection, определения standalone commit rows и
  распознавания exact `# CSharpGit: change-author begin/end` blocks является
  подготовкой raw text, а не новым rebase engine. Unknown/user commands,
  comments и blank lines остаются raw Git text; единственным interpreter todo
  остаётся установленный Git.
- Generated explicit-author command shell-quotes полный `Name <email>` как один
  argument; quoting и author validation принадлежат Git layer, а не XAML/code-behind.
  Generated reset-author command не содержит identity literals и распознаётся
  CSharpGit как собственный marker block наравне с explicit-author form.
- CSharpGit использует `GIT_SEQUENCE_EDITOR` только для передачи пользовательского
  todo настоящему Git. Raw workflow не устанавливает no-op `GIT_EDITOR`;
  `reword`, `squash`, `fixup -c` и другие editor-requiring commands используют
  обычную Git editor semantics.
- CSharpGit-started rebase хранит небольшой mode marker в
  `.git/csharpgit-rebase/`. Managed rebase может применять CSharpGit no-op editor
  и на Continue; raw и external/unknown rebase при Continue не получают его.
- Результат rebase определяется не только exit code. После initial start и Continue
  фактический repository state определяет `Completed`, `Conflicts`, `Paused`
  или `Failed`.
- Support files raw/managed rebase сохраняются во время active rebase и удаляются
  после полного completion или Abort; ошибка без active rebase также очищает
  CSharpGit-owned support files.
- Repository-level entry points используют общий presentation/mutation workflow;
  selected-path stash переиспользует тот же mutation lifecycle и authoritative refresh.
- CSharpGit не вводит собственный stash format: mutation и read model строятся поверх
  стандартных Git stash commits/parents. Shared history diff и tracked snapshot
  infrastructure переиспользуются там, где их semantics совпадают.
- Stable stash identity — stash commit. Positional `stash@{N}` является только
  текущим display/destructive-operation locator и не используется как cache identity.

## Non-Goals

- Копирование UI Git Extensions для interactive rebase.
- Visual/text dual mode для Interactive Rebase.
- Собственный parser или DSL для `git-rebase-todo`.
- `--rebase-merges`, root rebase и autocomplete.
- Встроенный полноценный commit-message editor для raw `reword`.
- GUI для `git rebase --edit-todo`.
- Cherry-pick, Revert и общий Reset workflow в обязательном MVP.

## Acceptance Criteria

- Пользователь может создать ordinary, staged-only и tracked+untracked repository stash
  через единый workflow из `Stashes` root или Commit area.
- Пользователь может stash один или несколько explicit Working Tree files, включая
  rename и selected untracked path, без изменения semantics из-за staged/unstaged side.
- Viewer показывает stash-specific details, union Changes с historical staging metadata,
  untracked content и полный tracked `W` snapshot отдельно от untracked `U`.
- Apply сохраняет stash; Pop и Drop защищены от stale positional identity; Drop требует
  явного destructive confirmation.
- Пользователь запускает merge выбранной branch и получает корректный Git outcome.
- Пользователь открывает Interactive Rebase как широкий raw multiline editor с
  line numbers, comment highlighting, рабочим horizontal scroll и встроенным
  comment help; может вручную менять команды/порядок/comments и запускает настоящий
  `git rebase --interactive`.
- History shortcut использует выбранный commit как `onto` и строит исходный todo только из следующих commits до текущего HEAD.
- В raw Interactive Rebase пользователь может применить `Change author…` к
  textual selection либо всем eligible commits, увидеть generated comment/`exec`
  blocks до запуска, повторно заменить собственный generated block и при желании
  вручную отредактировать или удалить его.
- Reset-to-current-identity генерирует стандартный Git `--reset-author` без
  встраивания name/email в todo; identity разрешается Git при выполнении rebase.
  Preserve AuthorDate является default, а explicit author остаётся отдельным mode.
- `Change author…` остаётся компактным: reset mode не показывает disabled
  Name/Email fields, redundant eligible-count text скрыт, action buttons остаются
  доступны без выхода flyout за пределы обычного desktop viewport.
- Conflict переводит merge/rebase в единый восстановимый conflict workflow.
- Non-conflict rebase stop остаётся active operation и возвращает `Paused`.
- После успешных или остановившихся operations UI соответствует фактическому
  repository state.
- Internal `Edit commit message…` продолжает использовать managed rewrite
  semantics и не открывает внешний editor.

## Verification

- UI contract tests проверяют dedicated raw editor, multiline/no-wrap todo,
  line-number gutter, comment highlighting, horizontal scrolling, встроенный
  comment help, отсутствие старого visual plan editor, отсутствие global/manual
  rebase entry и contextual raw entry path из History.
- Author-change unit tests покрывают caret/partial selection, aliases,
  squash/fixup exclusion, arbitrary user `exec`, own/malformed marker blocks,
  repeat Apply, LF/CRLF preservation, explicit validation/shell quoting и обе
  generated формы: `--author` и `--reset-author`.
- Integration test на реальном temporary repository запускает generated raw todo и
  проверяет multi-commit explicit author rewrite, native reset-to-current-identity,
  отсутствие identity literal в reset todo, сохранение AuthorDate/tree/message по
  умолчанию, optional date reset и отсутствие shell injection. Presentation
  contract отдельно подтверждает, что Apply только меняет raw text, compact flyout
  использует shared design-system resources и не запускает Git.
- На реальных test repositories проверяются initial todo, reorder, drop, raw
  commands вне `RebaseAction`, comments/blank lines, stale snapshot, conflicts,
  `break`, `edit`, failed `exec`, invalid todo, Continue и Abort. Отдельный regression
  test покрывает три commit-строки после выбранного `onto`, где средняя строка
  `fixup` схлопывается в предыдущую, rebase завершается, а текущая branch остаётся
  на переписанном HEAD.
- Отдельно проверяется, что raw Continue не получает CSharpGit no-op
  `GIT_EDITOR`, а существующий managed history rewrite сохраняет текущую editor
  policy.
- Для каждого workflow проверяются success и применимые failure scenarios,
  обновление UI и сохранение Git semantics.
